# KudaVPN — передача состояния работы

Состояние на **19 октября 2026 года**, дополненное результатами проверки после смены root-пароля. Цель файла — продолжить работу с текущего места. Это фиксация состояния, а не разрешение на развёртывание.

## Подтверждённая архитектура и границы

- **DigitalOcean Frankfurt** остаётся центральным контуром: действующий Telegram-бот, данные пользователей/подписок, PostgreSQL и связанные платёжные процессы. Состояние этих production-процессов в данном сеансе заново не проверялось; ничего там не изменялось. Рабочий Xray DigitalOcean не входит в пилот.
- **JustHost** — уже оплаченный отдельный VPN-хост. На нём существуют Xray-входы TCP/443 и TCP/8443 и изолированный управляемый пилот TCP/9443. Последняя проверка SSH показала, что все три порта прослушиваются процессами Xray. Это проверка слушателей, а не новый сквозной сетевой тест из России.
- **9443**: отдельный Xray-процесс VLESS + TCP + REALITY + Vision, один тестовый UUID, отдельные конфигурация/ключи/журналы и управляющий агент. Xray API доступен только на loopback; управляющий mTLS API пилота также привязан к loopback. Службы `kudavpn-pilot-node.service` и `kudavpn-pilot-control.service` при последней проверке были `active/running`. Рабочий `kudavpn-xray-alt8443.service` и `xray.service` также были `active/running`. Имена служб важны: похожие предполагаемые имена из первоначальной проверки оказались неверными.
- Владелец подтвердил на Android/Happ через домашний Wi-Fi в России: пилот 9443 воспроизводил YouTube и открывал Google/Cloudflare; один ранний запрос к example.com не прошёл. После блокировки пилотного UUID трафик остановился, после восстановления **того же** UUID прежний профиль Happ вновь работал без нового QR. Статический 8443 тоже ранее работал через Happ. Это не подтверждает стабильность во всех сетях, поведение многих клиентов или HTTPS-подписку.
- Письменное разрешение JustHost по [заявке №986998](https://my.justhost.ru/tickets/view/986998), сохранённое в материалах PR №6: публичный платный VPN, персональный доступ и Xray/VLESS/REALITY/Vision допустимы; отдельного тарифа не потребовали. Действуют лимиты скорости тарифа и правила против злоупотреблений. Перед массовым запуском сверить оригинал и актуальные условия.

## Доступ к JustHost и ротация root-пароля

- Подлинность SSH-хоста проверялась по ранее закреплённому ключу; соединения не принимали новый host key автоматически. Отдельный административный Ed25519-ключ установлен **с добавлением**, а не заменой существующих записей. Приватный ключ и фраза к нему находятся только вне Git.
- **До изменения** создана резервная копия `authorized_keys`. После добавления побайтовое сравнение подтвердило сохранность исходного содержимого; права файла остались `0600 root:root`. Точные пути восстановления хранятся только в частном операторском экземпляре этого отчёта.
- Успешно проверены два **отдельных** SSH-сеанса: новый ключ при запрещённой парольной аутентификации и прежний парольный вход при запрещённом public-key входе. Это подтверждает сохранение обоих способов SSH-доступа. Наличие резервной консоли провайдера не следует считать подтверждённым лишь по успешному SSH.
- На момент первоначального снимка root-пароль ещё не был заменён. Позднее владелец выполнил смену через Mac Terminal и получил `passwd: password updated successfully`. Значение нового пароля и сведения о его хранении в Git не записаны. Вход именно по новому паролю отдельно не проверялся; повторно менять его не требуется.

### Повторная проверка после публикации, 19 октября 2026

- Вход по новому административному SSH-ключу с проверкой закреплённого host key снова успешен. `xray.service`, `kudavpn-xray-alt8443.service` и `kudavpn-pilot-node.service` активны; TCP/443, 8443, 9443 слушают. Локальные порты пилотного Xray API и mTLS-агента также слушают.
- `kudavpn-pilot-control.service` теперь в состоянии `failed` с результатом `timeout`: она завершилась ровно через заданный `RuntimeMaxUSec=1d`, а `Restart=no`. Это соответствует ограниченному времени пилота. **Служба не перезапускалась.** Работа единственного пилотного доступа после прекращения продления аренды заново не проверялась; не считать его действующим только потому, что порт 9443 слушает.

### Проверка после смены root-пароля, 19 октября 2026

- Новый **отдельный** SSH-сеанс под root по административному ключу успешно прошёл с проверкой ранее закреплённого host key. Парольная аутентификация для этой проверки была запрещена; временный SSH-сеанс прежнего запуска не использовался.
- `xray.service`, `kudavpn-xray-alt8443.service` и `kudavpn-pilot-node.service` — `active`. Процессы Xray слушают TCP/443, 8443 и 9443. Это проверка служб и слушателей, а не новый тест трафика через Happ.
- `kudavpn-pilot-control.service` остаётся в состоянии `failed` (ранее зафиксирован тайм-аут ограниченного пилота). Служба не перезапускалась; считать управляющий агент работающим сейчас нельзя.
- Все файлы в `/etc/xray` имеют время изменения **раньше**, чем `/etc/shadow` после смены пароля; для конфигураций 443 и 8443 это проверено отдельно. Признаков изменения VPN-конфигураций в ходе ротации нет. Побайтовое сравнение с прежними закрытыми копиями в этом сеансе не выполнялось.
- SSH-настройки, Xray, агент, firewall, база данных и платежи в ходе этой завершающей проверки не менялись.

## Что подготовлено, но не запущено

- Тестовый Telegram Compose-контур в PR №6: своя PostgreSQL, отдельный том и токен BotFather, защита от наследования production `DATABASE_URL`, опциональный HTTPS feed на loopback. Токен тестового бота ещё не предоставлен; ни bot polling, ни миграции тестовой БД, ни публичный HTTPS ingress не запускались.
- Отдельный второй Xray/агент для нового тестового пользователя — **только шаблоны**. Кандидат TCP/10443 требует живой проверки свободного порта, firewall и ресурсов и отдельного разрешения на установку/правило. Существующий одно-пользовательский 9443 нельзя автоматически передать боту или увеличить лимит; его тестовый UUID не менять.
- HTTPS-подписка Happ с доверенным сертификатом ещё не доступна. Проектного домена нет. Для короткого пилота в документации PR №6 рассмотрено предоставленное JustHost имя в `vm.mydomain.zone`, но нужны подтверждение права его использования/стабильности, DNS, ACME, портов, ingress и фактический импорт `https://.../s/...` в Happ. Прямой QR пилота 9443 **не является** проверкой обновляемой HTTPS-подписки. Персональные ссылки не публиковать.
- mTLS-туннель/конфигурация доступа тестового Telegram-контура к **новому** агенту подготовлены шаблонами, но живой путь от контейнера и проверка сертификата ещё не пройдены. Управляющий API пилота 9443 остаётся на loopback.
- Цикл «имитация оплаты → бот → ссылка Happ → новый тестовый узел → продление → блокировка/истечение → восстановление» покрыт кодом и локальными тестами, **но не проведён сквозь настоящий тестовый Telegram-бот, публичный HTTPS feed и Android**. Реальных платежей не было.

## Очерёдность продолжения

1. **P0 — безопасность доступа.** Root-пароль заменён владельцем; новый SSH-вход по ключу подтверждён. При удобном отдельном окне проверить вход по новому паролю и резервную консоль провайдера, не меняя пароль повторно и не отключая рабочий доступ по ключу.
2. **P1 — изоляция пилота.** Прочитать свежие PR №5/№6 и CI, проверить статус 8443/9443 и ресурсы/порты/firewall **только на чтение**. Согласовать отдельное разрешение на второй изолированный узел для нового UUID; 9443/8443 не переиспользовать и не перезапускать.
3. **P1 — HTTPS Happ.** Сверить выданное JustHost FQDN, DNS/ACME и возможность доверенного TLS на отдельном порту без занятия 443. Защитить bearer URL от журналирования. До живого импорта на Android не объявлять подписку совместимой с Happ.
4. **P1 — отдельный бот/БД.** Владелец создаёт отдельного BotFather-бота и сохраняет токен вне Git/чата; после отдельного разрешения запустить тестовую PostgreSQL, применить миграции, проверить mTLS к **новому** агенту и один изолированный тестовый аккаунт. Не использовать production-токен/БД.
5. **P2 — сквозное испытание.** Фиктивно подтверждённый платёж, однократная активация, персональная HTTPS-ссылка, импорт в Happ, трафик из России, повтор события, продление без смены UUID/ссылки, блокировка и разрыв старого туннеля, естественное истечение аренды, восстановление, отказ агента. Проверять отсутствие влияния на 8443/9443 и отсутствие секретов в логах.
6. **P2 — коммерческий запуск позднее.** Отдельно разработать/проверить реальный YooKassa adapter/webhook, СБП при доступности магазина, резервное копирование/восстановление БД, мониторинг и нагрузку. Никаких реальных платежей или production cutover до отдельного решения владельца.

## Стоп-условия и ограничения

- Без нового разрешения **не** менять root-пароль, SSH-аутентификацию, firewall, общие маршруты, работающие Xray 443/8443/9443, production DigitalOcean, Telegram-бота, PostgreSQL, YooKassa, подписки и тестовый UUID 9443.
- Не объединять PR, не развёртывать тестовый контур/агент/HTTPS ingress, не покупать домен или услуги, не запускать платные продажи. Не отключать «Щука VPN» и не проводить прямые сетевые тесты из России без участия владельца.
- Не сохранять в Git пароли, токены, приватные ключи, UUID пользователей, QR, VLESS URI, персональные `/s/<token>` ссылки, mTLS-материалы или полные приватные конфигурации. Доступ к существующим приватным материалам — только из `KudaVPN-private`/«Паролей» macOS с проверкой прав; содержимое не копировать в отчёты.
- Известные риски: вход по новому root-паролю и независимый консольный доступ ещё не доказаны; управляющая служба пилота сейчас `failed` после ранее зафиксированного тайм-аута; PR №6 зависит от незамерженного PR №5; тестовая БД/бот/HTTPS feed не развёрнуты; второй узел и порт 10443 не проверены вживую; сертификат и журналы bearer URL требуют проверки; один успешный маршрут Android не гарантирует устойчивость у всех операторов; реальная платёжная интеграция не готова.
