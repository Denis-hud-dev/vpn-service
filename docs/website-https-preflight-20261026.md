## Почему развёртывание остановлено

Владелец прямо потребовал остановиться, если нужны BotFather/домен/DNS/иное решение. Нужны **BotFather и конфигурация OIDC**: в известных приватных каталогах не обнаружены подготовленные website/OIDC-файлы. Обычный API token тестового бота не заменяет OIDC Client Secret. [Официальная инструкция Telegram](https://core.telegram.org/bots/telegram-login) требует Allowed URLs и отдельные Client ID/Secret.

Кроме того, текущий PR29 — прототип сайта для нескольких подтверждённых аккаунтов, **не готовый закрытый owner-only perimeter**: `/` и статические страницы публичны; валидный вход другого Telegram-пользователя не ограничен allowlist. Публиковать исходный entrypoint наружу без доработки нельзя. Локальный fixture-login недопустим на сервере.

Отдельная `kudavpn_website_test` не имеет права записи в рабочую БД и не содержит рабочих UUID. Это необходимая изоляция, но она сама по себе не обеспечивает выдачу настоящего профиля из прежнего feed. Нельзя копировать активные подписки и запускать второй controller. Полный тест с реальным Happ пока не выполнен и не объявляется успешным.

## Предлагаемый закрытый контур после подтверждения

1. Оставить существующее имя/сертификат, использовать только свободный20443; проверить принятие этого origin/callback в BotFather. Поддержка числового порта формой регистрации в этой сессии не проверялась. При отказе не подменять URL и не занимать443/8443: согласовать другой адрес/маршрут.
2. Добавить owner allowlist из уже подтверждённой приватной конфигурации. Проверять её **до** записи User/WebIdentity/session. Неприглашённый вход не получает данные и не создаёт аккаунт. Снаружи доступна только минимальная форма входа; сама главная, кабинет, документы и API доступны лишь авторизованному владельцу. Не публиковать открытую демо-страницу.
3. Новый непривилегированный service user без shell/sudo, собственные каталоги/настройки, закрытые credentials и ограниченные systemd service/MemoryMax/CPUQuota. Не изменять общий reverse proxy, firewall, Xray или службы ботов. Текущий entrypoint loopback-only; наружное связывание20443 разрешать только после внедрения закрытого периметра и его тестов.
4. Новая отдельная тестовая БД/роль, только синтетические пользователи/заказы, миграция0009 только там. Приложение не получает рабочий DATABASE_URL, права на рабочие таблицы, admin SSH или реальные VPN-credentials. Покупка — явная имитация либо согласованный sandbox, без live-ключей/СБП.
5. Для реального Happ нужен отдельный согласованный read-only путь к существующей личной странице владельца либо независимый управляемый тестовый профиль с единственным источником истины. Эти варианты не равны автоматической выдаче после имитации. Выбрать и проверить план до доступа сайта к настоящим профилям; не выдавать заглушку за VPN.
6. Проверить с Mac/Android TLS, запрет анонимного/чужого доступа, OIDC/state/PKCE, кабинет/суммы/дубли/историю и отсутствие секретов в access/error logs. Тест реального клиента выполняет владелец; до него никакого заявления об успешном новом E2E.
