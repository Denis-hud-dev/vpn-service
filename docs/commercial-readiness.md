# KudaVPN: состояние перед платным запуском

Этот документ описывает локальную ветку разработки. Изменения не развёрнуты на
DigitalOcean и не включают реальные платежи.

## Уже реализовано

- Telegram: шесть разделов Premium, inline-навигация с обновлением одного
  экрана, тарифы 299/799/2490 ₽, сведения о подписке без выдуманных данных,
  инструкция для Happ. Состояние экрана хранится в PostgreSQL.
- Подписки: `pending`, `active`, `expired`, `blocked`, продление и история;
  повторное подтверждение одного платежа не продлевает срок дважды. Без
  `PaymentVerifier` активация отклоняется.
- Happ: персональный HTTPS bearer-токен хранится как хэш, одна ссылка может
  содержать несколько узлов, список обновляется по данным PostgreSQL. Узел
  показывается только при подтверждённой аренде доступа и свежем успешном
  контроле его агента и Xray. Истечение/блокировка скрывают список и дают
  агенту команду отзыва UUID. Сам агент удаляет доступ при истечении короткой
  аренды, даже если центральный сервер недоступен.
- Telegram: в новой локальной ветке при включённом HAPP_LINK_SECRET и готовом
  узле бот показывает владельцу персональную ссылку в прежнем интерактивном
  экране. Для новых ссылок в БД хранится nonce, а ключ остаётся вне БД; повторное
  открытие и продление сохраняют тот же URL. На production это не включено.
- Платежи: офлайн-слой сверяет окончательный ответ YooKassa с локальным заказом
  (статус, `paid`, `metadata.order_id`, сумму, валюту и время). Он принимает
  **только независимо полученный ответ** через внедрённый доверенный lookup.
  Реального HTTP lookup, webhook и ключей в приложении пока нет; по умолчанию
  верификация отключена. Функция не проводит оплату.
- Заказ: отдельный локальный orchestrator создаёт `pending` с ключом
  идемпотентности, передаёт ID заказа в metadata провайдера и принимает только
  HTTPS-ссылку оплаты с явно разрешённого домена. Повтор того же ключа не
  создаёт второй заказ. Он работает лишь с внедрённым тестовым gateway; бот его
  не вызывает.
- Уведомления: локальный обработчик получает по ID независимое состояние у
  провайдера и только после сверки с заказом активирует, игнорирует повтор или
  отмечает отмену. Тело webhook не считается доказательством. Реальный endpoint
  и авторизованный GET-адаптер не реализованы.
- Администратор: подготовлен отключённый от бота read-only обзор агрегатов,
  который проверяет разрешённый Telegram ID до обращения к БД. Управление
  клиентами, тарифами и узлами и аудит действий ещё не реализованы.

## Обязательные проверки перед продажами

1. Получить рабочий VPN-маршрут из России и подтвердить Happ на Android без
   стороннего VPN: импорт, HTTPS, DNS, Telegram, YouTube, повторная проверка.
   Состояние агента Xray само по себе такого результата не доказывает.
2. Развернуть отдельный HTTPS-домен подписок с TLS, закрытым API узлов, mTLS,
   ролями БД, защитой URL-токенов в ingress/логах, ограничением запросов и
   резервным копированием. Проверить миграции и откат на копии БД. Подключать
   каждый узел отдельно только после проверки маршрута из России.
3. Подключить выдачу ссылки в Telegram лишь после готовности HTTPS и VPN-узла.
   Для старых одноразовых ссылок nonce отсутствует: продумать явную миграцию без
   незаметной смены URL. Доделать отзыв/ротацию по запросу пользователя.
   Проверить импорт формата на настоящем Android Happ.
4. Для YooKassa: отдельный тестовый магазин и ключи, строго серверный GET
   платежа по ID из уведомления, проверка соответствия заказа, идемпотентный
   webhook, сценарии отказа/повтора/тайм-аута, затем ручная проверка возвратов
   и чеков. СБП включать лишь если способ доступен конкретному магазину.
   Настоящие ключи и проведение платежей требуют отдельного решения владельца.
5. Проверить отключение новых и уже открытых Xray-соединений после отзыва,
   доступность узла из клиентских сетей, мониторинг и аварийные процедуры.
   Текущий контроль узла проверяет агент, API и локальный listener, но не
   доступность публичного адреса и не исходящий интернет.
