## Безопасное получение реквизитов и ID — без запуска Support

Прежний `support_bot.setup_config` требовал заранее известные ID. Для этой задачи подготовлен отдельный `support_bot.bootstrap`, который получает настоящие ID через подтверждения владельца. Это **не** `support_bot.main`, не dispatcher, не демон и не фоновый polling.

На Mac создан ярлык (0700):

```sh
/Users/gr/Documents/KudaVPN-private/support/setup-support.command prepare
```

1. Владелец вводит точный username **нового Support-бота** и токен в скрытый запрос. Токен не вводить в аргументах команды, чате или браузерной адресной строке.
2. Помощник проверяет конфигурацию и выполняет только `getMe` и `getWebhookInfo` по HTTPS непосредственно к `api.telegram.org`, с проверкой сертификата, без redirect/прокси из окружения. Основной, TEST-бот и Monitor отклоняются существующими ограничениями. При неожиданном username или активном webhook подготовка останавливается; webhook не удаляется.
3. Токен сохраняется только на Mac вне Git: `/Users/gr/Documents/KudaVPN-private/support/bot-token` (0600). Метаданные и случайная одноразовая команда — в `bootstrap.json` (0600), каталог 0700. Существующие файлы не перезаписываются.
4. Терминал покажет команду вида `/support_setup_<случайный код>`. Владелец отправляет **эту точную команду от своего аккаунта** в два места: личный чат нового бота (сначала Start, если требуется) и созданную закрытую группу операторов. Не отправлять её анонимно от имени группы, не пересылать. Ответа бота пока не будет — это ожидаемо.
5. После отправки выполнить:

```sh
/Users/gr/Documents/KudaVPN-private/support/setup-support.command collect
```

6. Помощник повторно проверит идентичность нового бота и отсутствие webhook, затем сделает **один** короткий `getUpdates` (`timeout=0`, без offset и allowed_updates). Обновления не подтверждаются и не сбрасываются; сырой JSON не печатается и не сохраняется.
7. Требуются два свежих точных сообщения от **уже известного владельца**, одно в его private-чате и одно ровно в одной группе. Нельзя назначить владельцем «первого написавшего». Пересылки, анонимные отправители, другие пользователи и неоднозначные группы отвергаются.
8. `getChat` подтвердит тип и отсутствие публичного username/алиасов; `getChatMember` подтвердит права нового бота и владельца. Владелец сообщил, что бот администратор: помощник это проверит, но не изменит права. Переданные права других ботов/групп не используются.
9. В `support.env` (0600) сохраняются **фактические** `SUPPORT_ADMIN_CHAT_ID`, `SUPPORT_OPERATOR_IDS` (пока только владелец), token и username. Для закрытого теста также `SUPPORT_TEST_USER_IDS` — только владелец. `identity-verified.json` хранится рядом приватно; ID не публикуются в репозитории/чате. Штатные пользователи сервиса автоматически операторами не становятся.

Возможны безопасные остановки: неправильный токен/имя, webhook, отсутствие двух сообщений, анонимное сообщение, несколько групп, публичная группа, нехватка прав или истечение 24 часов. Ничего не обходить. Команда `collect` не запускает цикл ожидания; при отсутствии сообщения повторяется владельцем после его отправки. В первой сотне pending updates должны быть оба подтверждения; при переполнении остановиться, не подтверждать старые обновления через offset.

Приватный файл конфига переносить на сервер только после разрешения. Не присылать token, файлы или сырые обновления в чат. Достаточно ответа **«Конфигурация подготовлена»** после успешного collect. Если ID неизвестны, вручную искать их не потребуется.

## Подготовленная изоляция

- Отдельный release/venv в `/opt/kudavpn-support/`, private environment в `/etc/kudavpn-support/`, состояние 0700 в `/var/lib/kudavpn-support/`.
- Только собственная SQLite, только v001 миграция нового Support. Никаких PostgreSQL DSN, записей в существующие БД, shared volume, backup/Monitor keys.
- Запуск один на токен и базу; lock, проверка bot identity, привязка базы к боту/группе, durable cursor/outbox остаются.
- Для теста private-пользователи только из `SUPPORT_TEST_USER_IDS`; операции операторов по отдельным chat ID + operator allowlist. Предварительный помощник записывает только владельца. Пустой тестовый allowlist означает публичный доступ и **запрещён для первого тестового запуска**.
- Новому unit подготовлены `MemoryHigh=128M`, `MemoryMax=192M`, `CPUQuota=20%`, `TasksMax=64`, `Nice=10`, `IOWeight=50`. Это ограничения будущего нового процесса, не изменения существующих cgroup/служб. В сочетании с отсутствием скачивания вложений они ограничивают влияние Support; абсолютная гарантия отсутствия общей нагрузки не заявляется.
- Нет нового health-порта: локальная health-команда проверяет собственную очередь/heartbeat. Monitor не перенастраивается. Диагностика подписок/серверов остаётся отключённой («Нет данных»).
