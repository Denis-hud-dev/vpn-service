Развёртывание остановлено до настройки настоящего OIDC и нового разрешения. [Текущая архитектура и инструкция](website-closed-review-20261026.md). Разделы ниже сохраняют описание платёжного прототипа и отдельного локального демо.

[Draft PR №29](https://github.com/Denis-hud-dev/vpn-service/pull/29) поверх №27. Владелец выбрал основной канал продаж: самостоятельный сайт с ЮKassa, включая СБП после подтверждения конкретного магазина. Telegram-бот остаётся кабинетом управления, подключения и поддержки; внешняя продажа цифрового доступа из бота не включается. База этой ветки — PR №27, коммит890599c. Production, Monitor, VPN, серверы, платежи и действующие подписки не менялись; серверного развёртывания нет.

## Что реализовано

- Главная `/`: исходный прозрачный знак KudaVPN, прежняя тёмно-синяя палитра, описание, преимущества без обещаний скорости/доступности сайтов, тарифы199/499/1790 ₽ и сценарий подключения.
- `/account`: собственный компактный экран, реальные данные выбранной БД — статус, тариф, окончание, остаток, имена подтверждённых узлов и персональная страница Happ, если выдача действительно готова. Недоступный агент/выдача отображаются как ожидание, без фиктивного доступа. Данные демо получены из временной БД, не из базы владельца.
- `WebsiteCheckout` расширяет существующий WebCheckout, сохраняя PaymentCheckoutService, проверку ЮKassa, SubscriptionService, HappService, версии цен, продление от текущего окончания и прежний персональный профиль. Вторая платёжная система не создавалась. Каждый запрос заказа дополнительно фильтруется по пользователю серверного сеанса.
- История собственных заказов и НПД-обязательств; сумма берётся из Payment, не от браузера. Карту/CVC сайт не принимает. СБП и боевые ключи выключены; в тестовом каталоге явно `sbp_available=false`.
- Черновики `/docs/terms`, `/docs/privacy`, `/docs/support`. Они помечены неутверждёнными, без выдуманных реквизитов/гарантий. Реальные продажи недоступны.

## Авторизация и сохранение идентичности

Использован [официальный Telegram Login/OIDC](https://core.telegram.org/bots/telegram-login) на самостоятельном сайте. Это авторизация сайта, не покупка внутри бота и не Mini App. Запрашиваются только `openid profile`, без телефона, фото и разрешения отправлять сообщения. JS третьих сторон не подключается: серверный Authorization Code Flow + PKCE S256.

Начало входа создаёт случайные state, browser-binding cookie и PKCE verifier. State/binding в PostgreSQL хешированы; verifier доступен только закрытой БД на10мин. Callback требует совпадения браузера и одноразового state, атомарно удаляет flow до обмена code. Повтор и конкурентный callback не создают вторую сессию. Перенаправление всегда на фиксированный `/account`, пользователь не выбирает return URL.

Code меняется сервером на токен через фиксированный HTTPS endpoint Telegram с отдельным Client Secret. PyJWT/cryptography проверяют RS256, ключ только с закреплённого JWKS, issuer, audience, exp, iat, sub и подписанный числовой `id`. `jku`/`x5u` из заголовка не используются. Нет fallback на неподписанные поля. Разрешён только RS256: настройку алгоритма в BotFather менять без совместимой доработки нельзя. При смене ключа неизвестный kid отклоняется, кэш обновится на следующем входе.

Только подтверждённый claim связывается с прежним User.telegram_id. Старый пользователь, подписка и профиль сохраняются, имя/username не затираются. Уникальная WebIdentity не позволяет привязать subject к другому пользователю. Telegram ID из URL/body не является доказательством; login route не принимает такие параметры. Это также означает: для v1 покупателю нужен аккаунт Telegram, email/password-вход не реализован.

Browser session: случайный256-битный cookie, в БД только digest и срок1ч; `__Host-`/Secure/HttpOnly/SameSite=Lax/path=/, logout отзывает запись. Все POST требуют Origin+CSRF. Callback и личные данные no-store/no-referrer; access log выключен, ошибки без payload/URL/токена. Нет localStorage, аналитики, сторонних шрифтов, загрузки фото или QR-сервисов. При будущей публикации reverse proxy тоже должен исключать query/body/cookie из журналов, особенно `/auth/callback`.

Глобальные ограниченные rate-limit buckets предназначены для закрытой приёмки. Для публичного нескольких-worker развёртывания нужны распределённые лимиты/защита от abuse и полный review; текущую реализацию нельзя объявлять масштабированной публичной auth.

## Реестр НПД

Канонический платёж остаётся в `payments`. Новые `npd_receipts` и `npd_receipt_events` в той же транзакционной БД содержат сумму брутто, окружение, текущее обязательство и идемпотентные события. В закрытых событиях сохраняется только непрозрачная ссылка на приватный документ, без публичного URL/ИНН; эта ссылка не возвращается покупателю.

Состояния: `test_not_required`, `pending`, `issued`, `delivered`, `error`, `void_pending`, `voided`. Формирование и передача чека различаются. Нельзя отметить тестовую оплату реальным issued/delivered. `issued` требует непрозрачного document_ref; переходы оператора требуют явного подтверждения и ключа операции; ошибки имеют ограниченные коды. Повтор того же события не дублирует запись, конфликт параметров отклоняется. После подтверждённого возврата опубликованного чека нужна корректировка; сформированный документ и история не теряются.

Отдельный фоновый reconciliation подхватывает подтверждённые платежи после прерывания до создания обязательства; не зависит от открытия пользователем истории. Не повторяет активацию, не создаёт платежи/возвраты и не ходит в ФНС. Это eventual-consistent очередь после прежней транзакции оплаты, а не заявление об атомарной общей операции с внешней ФНС. Бэклог обрабатывается ограниченными порциями.

**ФНС и доставка ещё не подключены.** Операционный API record — внутренняя основа для будущего защищённого back office, не публичный HTTP endpoint и не готовая админка. Реальная загрузка/проверка документа, отправка покупателю, контроль сроков и утверждённый процесс возврата остаются до запуска. Подтверждение оператора должно следовать за реальным действием, не заменять его. Нет неофициального входа в «Мой налог» и хранения его пароля.

Продавец НПД/без НДС, [SELLER_PROFILE.md](SELLER_PROFILE.md). [ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics) требует отдельно зарегистрировать доход в «Моём налоге» и передать чек; автоматическая опция НПД у ЮKassa недоступна. [ФНС](https://npd.nalog.ru/faq/) определяет сроки выдачи и корректировки. Квитанция эквайера не считается чеком НПД. Live-реестр испытан только офлайн с синтетическими платежами; настоящих чеков не формировали.

## Изоляция и миграция

Миграция `0009_website` добавляет пять таблиц; не переписывает User/Payment/Subscription, UUID или цены. SQLite upgrade/downgrade и metadata проверены; CI использует свой disposable PostgreSQL. **На серверах миграция не запускалась.** Общий Database.check совместим с0008/0009, новый entrypoint требует0009.

`python -m bot.subscription_api.website_main` — подготовленный HTTPS review entrypoint. Только `KUDAVPN_SITE_MODE=review-test`, отдельная локальная PostgreSQL `kudavpn_website_test` под одноимённой ролью, разрешённый test shop1503208 и `test_` ключ. Рабочую `kudavpn_telegram_pilot` и production этот entrypoint отклоняет. Привязка только127.0.0.1; порты443/8443/9443/10443/18443/18543 запрещены. Автозапуска и развёртывания в этой ветке нет.

Необходимые приватные настройки будущего закрытого HTTPS-стенда: `DATABASE_URL`, `SITE_PUBLIC_ORIGIN`, `SITE_PORT`, `SITE_TLS_CERT`, `SITE_TLS_KEY`, `SITE_OIDC_CLIENT_FILE`, `SITE_OIDC_SECRET_FILE`, `SITE_TEST_SHOP_FILE`, `SITE_TEST_SECRET_FILE`, `SITE_SUBSCRIPTION_ORIGIN`, `SITE_HAPP_SECRET_FILE`. Credential files абсолютные, без symlink, доступ только владельцу; каталоги700. Хранить вне Git, например в приватной папке владельца; значения в чат не присылать. Если используется systemd Credentials0440, сначала копировать в закрытый StateDirectory600 — строгая проверка не ослабляется.

**Перед реальным подключением к существующим профилям** нужен отдельный план единой канонической БД сайта/бота/feed и работников выдачи. Нельзя запустить два управляющих процесса из независимых копий БД с одинаковыми UUID/узлами. Ветку0009 нельзя вслепую применить к нынешнему работающему тестовому боту: его старый runtime проверяет0008 при старте. Сначала закрытая копия без agent-доступа, backup/restore и проверка совместимого runtime; переключение только после разрешения. Новый entrypoint сам не регистрирует узлы, не запускает reconciler с реальным gateway и не изменяет Xray. При незавершённой интеграции кнопка не обещает готовый доступ.

Боевой адаптер/секреты, live-магазин, реальные СБП, webhook, автосписания, публичная публикация и платные ресурсы отсутствуют. Прежние чек-аут и тестовый бот на JustHost продолжают работать как раньше; Monitor/DO не затрагивались.

## Локальная демонстрация

Из корня ветки с установленными requirements:

```sh
python -m scripts.preview_website --port 18106
```

Открыть **http://127.0.0.1:18106/**. В подготовленной среде Codex дополнительные зависимости находятся только в `/private/tmp/kudavpn-site-deps`; запуск использует PYTHONPATH этого каталога и прежнюю локальную venv. Это не зависимость серверов, обычная установка requirements в новом venv заменяет временный каталог.

1. Посмотреть главную, тарифы и черновики документов.
2. «Войти через Telegram» в демо ведёт **только** на локальный fixture-login; надпись об имитации видна всегда. Настоящая OIDC-проверка покрыта отдельными криптографическими тестами, но с живым Telegram не выполнена. У review-приложения нет `/__demo__/login`.
3. Выбрать тариф → локальная имитация провайдера → «Имитировать успех» либо отмену. Никаких банковских реквизитов, настоящей ЮKassa или списаний здесь нет.
4. Проверить новый срок, историю и «Подключиться через Happ». QR/ссылка демо — заглушки, не импортировать на телефон. Дата демонстрационного подключения берётся из той же подписки временной БД.
5. Повторная проверка не добавляет срок. Выбор нового тарифа после успешной покупки проверяет продление. Демо-БД удаляется при остановке; сохранённые данные владельца не затрагиваются.

Скриншоты: `docs/screenshots/site-home-desktop.png`, `site-home-mobile.png`, `site-account-desktop.png`, `site-account-mobile.png`. Это синтетический аккаунт. ## Проверки и действия владельца

Новый `tests/test_website.py`: подписанные RSA/JWKS fixtures, подмена issuer/audience/подписи/алгоритма/claim, истечение и future iat, state/cookie/PKCE, конкурентный повтор callback, новый аккаунт и конфликт identity, отзыв/перезапуск сеанса, CSRF, чужие заказы/чеки, сохранение старого пользователя, покупка/продление/дубли, восстановление реестра и состояния НПД, ограничения review-конфигурации и cookie/заголовков. Старые платёжные/миграционные/навигационные тесты также проверяются. Локально **101 passed, 2 skipped** в профильном наборе; **24 случая** относятся к новому сайту. Пропуски требуют disposable PostgreSQL, который запускается в CI. После последней проверки разделения окружений повторён только файл сайта. Актуальный результат CI — в Checks нового Draft PR.

Владельцу до закрытого HTTPS-теста:

- Утвердить внешний вид и модель входа через Telegram; если нужен независимый email/passkey-вход, это отдельное расширение аккаунтов, не готовая функция.
- Выбрать существующий HTTPS origin для закрытого стенда; в BotFather → Login Widget зарегистрировать origin и точный `/auth/callback`, получить **отдельные** Client ID/Secret. Это не обычный BotFather API token. Хранить секрет в приватном файле600, не в чате. Настройки бот-аккаунта в этой сессии не менялись.
- Утвердить отдельный план БД/выдачи и разрешить закрытое развёртывание с backup/rollback; не переносить рабочие UUID между конкурирующими контроллерами.
- Согласовать документы, реальные контакты/реквизиты продавца и процесс выдачи/доставки/корректировки чеков НПД.

Затем провести настоящий OIDC и sandbox E2E с двумя тестовыми аккаунтами. До первых реальных продаж потребуются отдельный live-контур, подтверждение условий магазина/СБП, фискальный рабочий процесс, возвраты и разрешение владельца. Рекомендации об отсутствии покупки внутри бота основаны на [Telegram Stars FAQ](https://core.telegram.org/bots/payments-stars#faq); вход через Telegram не используется для обхода правил. Структура пользовательского пути остаётся предметом приёмки перед публикацией.
