# KudaVPN: минимальный план поиска причины отказа из России

Дата: 13 октября 2026 года. **Исторический план:** пункт о поиске другой сети заменён [планом для домашнего Wi-Fi от 14 октября](home-wifi-recovery-2026-10-14.md) по прямому указанию владельца. Команду из этого документа не запускать. Цель — работающий Happ на Android напрямую из России, подтверждённый владельцем на обычном домашнем Wi-Fi.

Исходные факты и ссылки на защищённые отчёты: [investigation-status-2026-10-13.md](investigation-status-2026-10-13.md). Сравнение JSON Happ: [happ-profile-comparison-2026-10-13.md](happ-profile-comparison-2026-10-13.md).

## Принцип: проверять слои в порядке прохождения пакета

`Android/Mac → домашний Wi-Fi/оператор → международный маршрут → сеть хостера → eth0 VPS → TCP-front/Xray → REALITY → VLESS → исходящий интернет → Happ/DNS/маршрутизация`

Менять fingerprint, SNI или DNS бессмысленно для прогона JustHost, в котором SYN не дошёл до `eth0`. Сначала установить, появляется ли TCP-поток на сервере. Если TCP появился, только тогда переходить к Xray и после него — к DNS и правилам Happ.

## Минимальный набор будущих проверок

### 0. Подготовка без сетевого теста

1. Сохранить экспорт **фактического** JSON импортированного KudaVPN-профиля из Happ в защищённой папке вне Git, предварительно закрыв адрес узла, UUID, public key, short ID и полную ссылку в материалах для обсуждения. Сравнить TUN/VPN-режим, SOCKS, DNS, sniffing и routing с документом о «Щуке». Этот шаг выявляет отдельную проблему клиента, но не объясняет исчезновение SYN в независимом тесте Mac.
2. Проверить наличие уже собранных отчётов и актуальность пути к автономному сценарию; не повторять те же проверки при неизменных условиях. Сервис Xray и базу не трогать.

### 1. Сетевой путь к JustHost: одна независимая российская сеть

Уже проверенная сеть дала 8 исходящих SYN Mac и ноль соответствующих SYN на `eth0` JustHost. Повторять это на том же Wi-Fi без изменения условий не нужно. Если доступен **другой российский провайдер** без покупки нового сервера (например, другая домашняя сеть или существующий хот-спот, но не недоступный Tele2), выполнить один 15-секундный парный тест Mac/JustHost с тем же числовым адресом и портом 443:

- серверный наблюдатель стартует **до** команды Mac, подтверждает готовность и сам завершается по лимиту времени;
- Mac проверяет маршрут `en0` без «Щуки», собирает только TCP-заголовки и делает один `connect` к 443;
- после теста серверный наблюдатель останавливается, сравниваются TCP flags, sequence/ACK и время. Не сохранять содержимое пакетов и клиентский публичный IP в проекте.

Если другой независимой сети нет, следующий минимальный шаг — **не новый тест**, а запрос в поддержку JustHost по уже зафиксированному окну 13 октября 2026 года, 14:51:58–14:52:13 PDT: видел ли их сетевой край входящие SYN на публичный TCP/443 VPS и действовала ли фильтрация/anti-DDoS. Адрес клиента, если он понадобится провайдеру, передавать только в закрытом обращении, не в Git и не в отчёте. Отправка обращения требует отдельного поручения владельца.

### 2. При появлении TCP: один тест Xray, без смены параметров

Только если SYN виден на сервере, SYN-ACK возвращается клиенту и завершающий ACK доходит до сервера, провести один короткий VLESS/REALITY/Vision-тест с **нашими** действующими параметрами. Одновременно наблюдать клиент, публичный 443, TCP-front (если есть), Xray и его исходящий поток. Запросить HTTPS к числовому IP через временный SOCKS/VLESS, чтобы сначала исключить DNS. Проверять по фактам:

1. TLS ClientHello дошёл до Xray и REALITY принят либо отклонён/переведён на target?
2. После принятия REALITY есть положительная VLESS-авторизация нашего UUID и flow?
3. После авторизации Xray открыл исходящий поток к запрошенному сайту и получил ответ?
4. Клиент получил HTTPS-ответ через VPN и отличается ли наблюдаемый внешний IP от прямого?

Предыдущий DigitalOcean v4 дошёл до Xray и исходящего соединения с REALITY target, но не получил ответ; успешная VLESS-авторизация не доказана. Не записывать новый «успех» на основании одного флага `reality_verified` в клиентском логе или HTTP-ответа напрямую с VPS.

### 3. Только после прохождения HTTPS через туннель: Android/Happ

На том же российском Wi-Fi проверить импортированное KudaVPN-подключение в Happ. Сначала — HTTPS к обычному сайту, затем YouTube/Telegram. Если через независимый Xray-клиент трафик идёт, а Happ нет, запросить один конкретный набор: экспорт обезличенного фактического JSON KudaVPN, экран VPN/TUN и диагностическое сообщение Happ. После этого проверять DNS, `UseIPv4`/IPv6, split-routing, direct/proxy, sniffing и автовыбор. Не менять несколько полей одновременно и не использовать реквизиты «Щуки».

## Как трактовать результат

| Наблюдение | Наиболее узкий подтверждённый вывод | Следующее действие |
| --- | --- | --- |
| SYN виден на Mac, не виден на `eth0` VPS | Потеря до гостевой ОС; это не ошибка Xray | Сравнить вторую сеть и/или данные сетевого края хостера. |
| В другой российской сети SYN доходит, в первой нет | Проблема зависит от исходного провайдера/маршрута | Исследовать первый маршрут и доступность альтернативных узлов; не объявлять универсальную блокировку хостера. |
| Сетевой край хостера видит SYN, гостевой `eth0` — нет | Вероятный участок внутри инфраструктуры хостера до VPS | Передать оператору времена и обезличенные метаданные. |
| `eth0` получает SYN, отправляет SYN-ACK; клиент не получает его | Потеря в обратном направлении между VPS и клиентом | Сопоставить захват на обеих сторонах; проверить обратный маршрут/фильтрацию. |
| TCP завершён, но REALITY отклонён/переведён на target | Проблема после TCP, на уровне REALITY или политики клиента | Сверить **свои** SNI/serverNames, key pair, short ID, fingerprint, версии и время. |
| REALITY принят, VLESS отклонён | Проблема авторизации VLESS | Проверить свой UUID, flow и состояние пользователя на узле. |
| VLESS принят, HTTPS по числовому IP не возвращается | Проблема исходящего соединения Xray/маршрута/ответа | Сопоставить outbound, серверный сокет и обратные пакеты. |
| HTTPS по числовому IP работает, сайты по именам — нет | Вероятнее DNS/IPv6/маршрутизация клиента | Проверить фактический Happ JSON и DNS-логи. |
| Независимый клиент работает, Happ нет | Отдельная проблема Happ/импорта/TUN/правил | Анализировать Happ, не менять сервер наугад. |

Один захват на `eth0` не может назвать точный промежуточный маршрутизатор. Даже одинаковый результат в двух сетях не доказывает блокировку IP: нужен ответ хостера или дополнительное независимое измерение.

Чтобы **разделить российский провайдер и промежуточный маршрут**, нужны наблюдения не только на Mac и VPS. Сначала сравнить результат из второго независимого российского ASN; если различие повторяемо, запросить у оператора/хостера маршрутную или anti-DDoS-телеметрию в конкретное время. Если домашний роутер умеет безопасно показывать исходящие SYN на WAN без перенастройки, это дополнительно отделит локальный NAT от провайдера. TCP traceroute/MTR может подсказать участок маршрута, но отсутствие ответа отдельного хопа само по себе не доказывает потерю пользовательского TCP. Если ни оператор, ни хостер не дают точку наблюдения между краями, честный итог — «потеря между интерфейсами, точный узел неизвестен», а не утверждение о блокировке.

## Инструкция владельцу, когда будет принято решение продолжить

**Сейчас ничего запускать не нужно.** Для парного теста сначала Codex подтвердит, что краткий серверный наблюдатель готов и автоматическое завершение настроено. Затем владелец:

1. Подключает Mac к выбранной российской сети; обычный интернет должен работать. Не использовать одновременно другой VPN для тестового маршрута.
2. Вручную отключает «Щука VPN». Codex не отключает её и не зависит от ChatGPT во время проверки.
3. В Terminal выполняет ровно одну команду:

   ```sh
   sudo /Users/gr/Documents/KudaVPN-private/diagnose-justhost-tcp-syn.command
   ```

   Пароль администратора Mac вводится только в Terminal по запросу `sudo`; сценарий его не получает и не сохраняет.
4. Дожидается сообщения `ПРОВЕРКА ЗАВЕРШЕНА. МОЖНО ВКЛЮЧИТЬ ЩУКА VPN`, снова вручную включает «Щуку» и отвечает «Готово». Отчёт останется в `~/Documents/KudaVPN-private/diagnostic-reports/`.

Не выполнять эту команду до сигнала о готовности серверного наблюдателя: иначе результаты не будут синхронными. Если альтернативная сеть недоступна, сообщить об этом вместо повторения теста на прежней сети.

## Ограничения и откат

- Никаких покупок, смены протокола, SNI, ключей, firewall, маршрутов и production-конфигураций. Без отдельного согласования выполнять только анализ существующих файлов.
- Будущие наблюдатели — временные, с тайм-аутом и очисткой; при ошибке останавливать только их. Xray, бот и PostgreSQL остаются работать.
- Новые отчёты в проекте — только обезличенные выводы. Сырые метаданные, профили и пароль VPS хранятся в `KudaVPN-private`, вне Git.
