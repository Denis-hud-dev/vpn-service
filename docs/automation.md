# Автоматическая проверка KudaVPN

Первый этап запускает GitHub Actions для pull request, push в `main` и в ветку
`codex/ci-foundation`, а также вручную. Временный runner использует Python 3.12 и
одноразовую PostgreSQL 16. Он проверяет отслеживаемые Git-файлы, зависимости,
синтаксис, offline smoke test, Alembic-миграции и тесты. Итог виден в Actions,
короткий отчёт — в Summary, JUnit XML хранится семь дней как артефакт.

В workflow нет Telegram polling, YooKassa, VPN-клиента, SSH, deployment и
доступа к DigitalOcean. `GITHUB_TOKEN` имеет только `contents: read`; checkout
не сохраняет учётные данные. Тестовая БД создаётся на runner и не содержит
пользовательских данных. Статическая проверка `check_repo_hygiene.py` выявляет
очевидные секреты и резервные копии в отслеживаемых файлах, но не заменяет
проверку diff перед публикацией и GitHub secret scanning.

При красном CI откройте упавший job, Summary и `pytest-results`. Воспроизведите
локально через `python -m pytest -q` без переменных production; PostgreSQL-тест
нуждается в отдельной пустой базе через `TEST_DATABASE_URL`. Исправления делайте
в рабочей ветке и повторно запускайте CI. Codex может анализировать конкретный
провал и готовить исправление в отдельной ветке; этот этап не даёт ему права
автоматически менять `main`, production или оплачиваемую инфраструктуру.

Следующий этап: подключить оставшиеся экспериментальные ветки к CI, добавить
проверки жизненного цикла подписок и Xray в изолированном окружении, затем
настроить автоматическую диагностику неуспешных run и подготовку PR без merge.
