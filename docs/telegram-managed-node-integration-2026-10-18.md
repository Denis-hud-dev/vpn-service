# Telegram → управляемый JustHost:9443: состояние интеграции

PR №5 (`codex/payment-admin-prep`) готовит локальный учёт заказов,
независимую проверку статуса у провайдера и идемпотентное применение успешного
платежа. PR №6 (`codex/justhost-happ-integration`) основан на №5 и добавляет
персональные Happ-ссылки, реестр узлов, сверку краткосрочных аренд UUID,
проверку здоровья и изолированный mTLS-агент Xray. Эти PR — черновики;
ни один компонент из них не переключал production-бота.

Владелец уже подтвердил работу отдельного JustHost:9443 на Android через
Happ и домашний Wi-Fi: блокировка пилотного UUID остановила Интернет,
восстановление **того же** UUID вернуло YouTube и сайты через прежний профиль.
Это проверка ручного пилота, а не платёжного пути или HTTPS-подписки.
Действующий JustHost:8443 и DigitalOcean не входят в управление PR №6.

## Проверенный сценарий на имитациях

`tests/test_managed_pilot_payment_flow.py` выполняет локально цепочку:

1. Неоплативший пользователь не получает ссылку. Для
   тестового заказа имитируется создание оплаты; состояние `succeeded`
   независимо возвращает имитация провайдера с правильными ID, суммой и
   валютой. Настоящие YooKassa и деньги не используются.
2. Подтверждение активирует срок, согласование выдаёт единственный UUID на
   узле TCP/9443; проверка здоровья разрешает персональную Happ-ссылку.
   Экран подключения Telegram показывает её только владельцу.
3. Повтор события того же платежа не продлевает срок и не создаёт новый UUID.
   Повтор idempotency key после исполнения заказа не создаёт новую оплату.
4. Истечение закрывает Happ-feed; согласование снимает UUID, перезапускает
   только имитацию пилотного Xray и закрывает имитируемый открытый туннель.
   Новый проверенный платёж восстанавливает прежние UUID и ссылку.
5. При недоступности агента выдача не подтверждается и ссылка скрыта. Если
   отзыв не применился, `revocation_confirmed` остаётся ложным до успешной
   повторной сверки. Второй оплаченный пользователь отклоняется лимитом
   одного UUID и не вытесняет первого.

Это проверка логики и границ отказа, не реальный Telegram/YooKassa/Xray
end-to-end. Отдельные тесты PR №6 проверяют mTLS, перезапуск управляемого
Xray, историю платежей, миграции и выдачу ссылки в интерфейсе бота.

## Что требуется перед ограниченной проверкой через Telegram

1. Выделить **отдельную тестовую БД** с миграциями PR №5/№6 и фиктивным
   Telegram-пользователем. Не подключать её к production-боту или его БД.
   Тестовое подтверждение оплаты разрешено только через имитацию провайдера.
   Настоящий YooKassa lookup/webhook и переключение кнопки оплаты бота пока
   не настроены; в `Services.persistent` платёж остаётся демонстрационным.
2. Подготовить отдельный доверенный HTTPS-домен, сертификат и ingress для
   `/s/<token>`, затем задать `SUBSCRIPTION_PUBLIC_URL` и отдельно хранимый
   `HAPP_LINK_SECRET` тестовому боту/API. Без домена ручной QR-профиль не
   заменяет проверку автоматической подписки. Запретить access log полного
   URL и общий кэш; токен ссылки даёт доступ к конфигурации.
3. Организовать защищённый маршрут управляющего сервиса к пилотному агенту,
   который сейчас слушает **только** `127.0.0.1:19443` на JustHost.
   Предпочтителен отдельный ограниченный SSH-туннель с mTLS поверх него;
   административный API и Xray API наружу не открывать. Проверить CA,
   клиентский сертификат, права файлов и отказ при потере туннеля.
4. Сейчас на пилоте лимит **один** UUID, уже занятый ручным тестом.
   Центральная БД не знает его lease/revision, поэтому нельзя объявлять
   этого пользователя управляемым ботом и нельзя создать второго на том же
   агенте. Нужен отдельно согласованный переход состояния либо новый
   изолированный пилот. До решения не менять действующий тестовый UUID,
   его срок и доступ.
5. В тестовой среде повторить: один фиктивный заказ → одна ссылка в личном
   чате → импорт в Happ → продление без нового QR → истечение/блокировка →
   отказ feed и фактический отзыв на узле → восстановление тем же UUID.
   Замерить время между блокировкой и прекращением уже открытого туннеля.
   Повторить при временной недоступности агента; неподтверждённый отзыв
   должен быть виден оператору и повторён. Убедиться, что 8443 исправен.

Для отката остановить только отдельные тестовые bot/API/tunnel-компоненты,
скрыть пилотный узел из тестовой выдачи и сохранить записи неподтверждённых
отзывов. Не трогать 8443 и production DigitalOcean. Публичная выдача платных
подписок запрещена до проверки реального платёжного адаптера, управления
несколькими клиентами и мониторинга фактических отзывов.
