# Изолированный Telegram-пилот: подготовка без развёртывания

**Статус:** конфигурация и проверки подготовлены в draft PR №6. Контур не
запускался, тестовый токен не получен, production-серверы и пилотный UUID
JustHost:9443 не менялись. Этот документ не разрешает включать реальные
платежи или переносить действующий UUID.

## Аудит зависимостей

- PR №5 основан на `codex/happ-link-delivery`: локальные заказы, стабильный
  idempotency key и обработка статуса только после независимого ответа
  провайдера. Нет реального YooKassa HTTP-адаптера/webhook и кнопки оплаты.
- PR №6 основан на PR №5: персональная HTTPS-ссылка Happ, отдельный UUID на
  каждого пользователя и узел, контроль здоровья, краткие аренды, mTLS-агент
  и фактический отзыв на отдельном Xray. Прежний JustHost:8443 не входит в
  управление. PR остаётся draft и не находится в production.
- Миграции образуют одну цепочку `0001` → `0007`. `0003`–`0007` в upgrade
  добавляют таблицы/колонки; существующие production-данные не удаляют.
  `Database.check()` требует ровно `0007_happ_link_nonce`, поэтому запуск
  нового бота на немигрированной production-БД закончится ошибкой. Для
  пилота разрешена **только новая пустая** `kudavpn_telegram_pilot`.
- Секреты: токен тестового Telegram-бота, пароль отдельной БД, HAPP_LINK_SECRET,
  ключи mTLS и TLS-сервера хранятся вне Git. Нельзя копировать production
  `BOT_TOKEN`, `.env.production`, ключи Xray или пользовательские ссылки.

## Тестовый бот и PostgreSQL

`deploy/telegram-pilot/compose.yml` имеет отдельное имя проекта, отдельный
том `pilot_pg_data` и PostgreSQL `kudavpn_telegram_pilot`. Её порт 55433
доступен только с localhost; бот не публикует HTTP-порт и запускается лишь
при явном профиле `telegram`. Миграции проходят до запуска бота. Пароль БД и
токен передаются как Docker secrets из двух **разных** приватных файлов;
файлы на хосте должны иметь права 0600. Внутренний launcher строит адрес БД
из фиксированного имени сервиса, пользователя и базы; попытка передать
`DATABASE_URL`/`DATABASE_URL_DOCKER` из старой среды прекращает запуск.
Числовой ID в токене должен совпадать с отдельно заданным ID тестового бота.
Это защита от случайного использования production-токена, но владелец должен
сверить бот-username при создании токена. Контур не использует `docker-compose.production.yml`.

Без публичного URL бот может показать меню и статус, но не выдать Happ-ссылку.
После подготовки доверенного HTTPS-адреса добавить только
`compose.happ.yml`, приватный 32-байтный base64url HAPP_LINK_SECRET и
`PILOT_SUBSCRIPTION_PUBLIC_URL`. В этом отдельном opt-in слое теперь есть
сервис `feed`: он читает ту же тестовую БД, опрашивает один настроенный агент
через mTLS и выдаёт `/s/<token>`. Docker публикует его TLS-порт **только на
127.0.0.1 хоста**. Приватный каталог `PILOT_FEED_PRIVATE_DIR` монтируется
только для чтения и должен содержать `tls.crt`, `tls.key`,
`agent-config.json`; ключ и конфигурация имеют права 0600 и доступны UID
10001 внутри контейнера. `agent-config.json` должен содержать только ID
второго тестового узла и проверенный mTLS endpoint. Токен Telegram и ключ
вычисления ссылок сервису `feed` не передаются. Публичный ingress,
сертификат, доступ контейнера к закрытому mTLS-туннелю и размещение контура
пока **не настроены и не проверены**. Healthcheck подтверждает локальный
TLS handshake с проверкой имени из URL; это не доказывает доступность из
России или успешную выдачу конкретной подписки. Bearer-токен
не должен попадать в access logs, общий кэш или аналитику URL.

Файлы подготовлены для проверки перед будущим запуском; никакие `up`,
миграции, polling или изменение БД сейчас не выполнялись. Статическая
проверка `docker compose config --quiet` для базового и Happ-слоёв прошла с
фиктивными файлами. Следующая реальная проверка начинается с резервируемой
пустой тестовой БД и отдельного BotFather-бота, после разрешения владельца.

## HTTPS-ссылка Happ без лишних расходов

В доступной конфигурации нет установленного `SUBSCRIPTION_PUBLIC_URL`; владелец
ранее сообщил, что отдельного домена проекта нет. Позднее в кабинете JustHost
обнаружено выданное VPS имя в зоне `vm.mydomain.zone`; публичные A/AAAA
совпадают с адресами VPS. Оно может подойти **для короткого пилота** после
проверки ACME, портов и условий пользования; это не домен KudaVPN. Подробный
preflight — в `docs/telegram-happ-first-e2e-checklist-2026-10-18.md`.
Самоподписанный сертификат не подходит для ссылки пользователя. Возможны:

1. **Предпочтительно:** поддомен уже принадлежащего проекту домена, если
   такой позже появится, с DNS, доверенным TLS и отдельным HTTPS ingress.
   Меньше эксплуатационного риска, но сейчас подтверждённого домена нет.
2. **Без покупки домена, для ограниченного пилота:** выданное JustHost FQDN
   с обычным доверенным сертификатом Let's Encrypt через HTTP-01 на TCP/80
   и отдельным HTTPS ingress. До выдачи ссылки проверить, что имя стабильно,
   TCP/80 доступен для ACME, сертификат обновляется, а Happ импортирует URL.
3. **Резерв без FQDN:** публичный IPv4 JustHost
   с доверенным IP-сертификатом Let's Encrypt и отдельным HTTPS-портом.
   [IP-сертификаты доступны](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability),
   но действуют около шести дней и требуют автоматического продления;
   [проверка IP](https://letsencrypt.org/2025/01/16/6-day-and-ip-certs)
   использует HTTP-01 на TCP/80 или TLS-ALPN-01 на TCP/443. Порт 443 уже
   занят действующим VPN. Доступность TCP/80, правила провайдера/firewall,
   отдельный HTTPS-порт, автоматическое обновление и импорт `https://IP:порт`
   в Happ на Android надо проверить **до** выдачи. Это потребует отдельного
   разрешения на новые службы и сетевые правила. Launcher допускает IP-URL
   только при явном `PILOT_ALLOW_IP_CERT=1`; сертификат он сам не выдаёт.

Для коммерческой эксплуатации предпочтительнее принадлежащий проекту домен.
Happ документирует обновление подписки по HTTP-заголовкам, но фактический
импорт нашего HTTPS-URL на Android ещё не проверен:
[документация Happ](https://www.happ.su/main/dev-docs/app-management).

## Закрытый путь к управляющему агенту

Пилотный агент слушает `127.0.0.1:19443` на JustHost. Публичный доступ к
административному API и Xray API не нужен. Подготовлен
`deploy/telegram-pilot/open-agent-tunnel.sh`: SSH с проверкой host key,
без запроса пароля и с локальным пробросом `127.0.0.1:19444` на серверный
loopback. `agent-config.example.json` указывает только локальный HTTPS URL;
реальные CA/client cert/key и ID узла заполняются **в приватном файле 0600**.
`scripts/pilot_agent_preflight.py` проверяет ровно один выбранный узел,
loopback URL, TLS-сертификат сервера, успешный mTLS health и отказ тому же
endpoint без клиентского сертификата. Скрипт делает только GET health, не
вызывает изменение доступа. Локальный тест одноразового mTLS-сервера прошёл;
живой туннель/сертификаты пилота ещё не проверены. При ошибке TLS проверку
останавливать, верификацию сертификата не отключать.

## Один **новый** пользователь: условия реального опыта

Существующий агент 9443 имеет лимит одного UUID, и место занято действующим
ручным пилотом. Увеличивать лимит или переподчинять этот UUID бот-контроллеру
без разрешения нельзя. Безопасный вариант — **второй независимый**
Xray-процесс/агент на том же уже оплаченном JustHost: отдельные TCP-порт
(кандидат 10443 после проверки), Xray API, конфиг, REALITY-ключи, mTLS CA,
state, systemd unit и один новый UUID. Это не требует нового VPS, но требует
проверки ресурсов/портов и отдельного разрешения на установку и точечное
сетевое правило. Рабочие 8443 и 9443 остаются под прежним управлением.

После подготовки отдельного узла и HTTPS endpoint проверить в такой
последовательности, используя **имитацию**, а не YooKassa:

1. В отдельной БД зарегистрировать одного тестового Telegram-пользователя,
   открыть тариф в тестовом боте. Текущий тарифный экран не запускает оплату;
   тестовый заказ и независимо подтверждённое фиктивное событие создаёт
   только изолированный операторский harness. Его повтор не меняет срок.
2. Дождаться подтверждённой аренды на втором агенте и свежего health;
   увидеть одну персональную HTTPS-ссылку в личном чате. Импортировать её в
   Happ и проверить реальные HTTPS/YouTube. Другой пользователь не получает
   эту ссылку или UUID.
3. Продлить тестовый срок другим фиктивным событием: срок увеличивается один
   раз, ссылка и UUID не меняются. Повтор события не добавляет срок.
4. Дождаться искусственно короткого истечения: feed отказывает, узел снимает
   UUID и закрывает прежний поток. Повторная попытка VPN не авторизуется.
   После фиктивного продления прежняя ссылка и UUID вновь работают.
5. Административную блокировку проверить отдельно: платёж **не** снимает её
   автоматически. Только после явного решения администратора возможен
   переход к продлению. При недоступности агента выдача скрыта, отзыв не
   получает ложного подтверждения и повторяется после восстановления.

Остановить опыт при изменении PID/доступности 8443 или прежнего 9443, появлении
неожиданного UUID, ошибке TLS, расхождении оплаченного статуса и фактического
доступа, попадании секрета в журнал. Откат — остановить **только** второй
тестовый узел/тестовый bot/API/tunnel, сохранить обезличенный отчёт и запись
неподтверждённого отзыва. Production и существующий пилот не трогать.
