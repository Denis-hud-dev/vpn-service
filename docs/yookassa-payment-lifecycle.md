# Платёжный цикл KudaVPN: тестовый контур и путь к запуску

Этот PR продолжает PR №5–13 и не развёрнут. Текущий `@KudaVPN_Test_Bot` уже использует тестовый магазин 1503208, изолированную PostgreSQL и опрос ЮKassa. Тарифы 299/799/2490 ₽, персональная HTTPS-подписка Happ, уведомления, продление, истечение и сверка доступа с агентом существуют в предыдущих PR; они здесь не дублируются. По сообщению владельца, одна тестовая оплата 299 ₽ и подключение в Happ уже проверялись. Этот PR не выполнял новый платёж и не читал секреты магазина.

## Что добавлено

- В `PaymentNotificationProcessor` входящий идентификатор теперь сначала должен совпасть с **уже привязанным** к локальному заказу платежом. Неизвестный ID не вызывает запрос к провайдеру. Письмо, браузерный возврат и тело webhook сами по себе не выдают доступ.
- В существующий HTTPS-сервис добавлен **выключенный по умолчанию** маршрут `/yookassa/test-webhook`. Он доступен только при `PILOT_PAYMENT_WEBHOOK_ENABLED=1`, маркере пилота, Telegram ID владельца и изолированной БД `kudavpn_telegram_pilot`. Из тела уведомления берётся только форматно проверенный ID; далее выполняется независимый аутентифицированный `GET /v3/payments/{id}` с тестовым магазином. Затем существующий код проверяет `test=true`, заказ, сумму, валюту, статус и однократное начисление. При недоступности ЮKassa маршрут отвечает 503; действующий опрос позже повторяет проверку. Тело, URL и секреты не пишутся в журналы. Без включения флага маршрут возвращает 404.
- HTTP-адаптер умеет сформировать запрос ЮKassa с `payment_method_data.type=sbp`, `capture=true` и `confirmation.type=redirect`. Выбор СБП в Telegram **не включён**: официальный тестовый магазин не позволяет проверить этот способ оплаты. Действующая кнопка ведёт на обычную страницу ЮKassa, где набор способов определяется магазином.

## Ограничение входящих уведомлений

ЮKassa требует публичный HTTPS URL на **443 или 8443** для HTTP-уведомлений. Изолированный feed KudaVPN сейчас находится на **18443**, а 443/8443 заняты работающим VPN и не подлежат изменению в этом PR. Поэтому нельзя зарегистрировать этот маршрут как реальный webhook тестового магазина без отдельного безопасного HTTPS-входа на разрешённом порту и согласования его с владельцем. Пока гарантированным автоматическим механизмом остаётся действующий опрос каждые 30 секунд. Настраивать URL в кабинете ЮKassa сейчас не нужно.

## Проверка и откат

Тесты используют фиктивный HTTP-провайдер и отдельную временную SQLite-БД. Проверяются подтверждённая оплата, повторное уведомление, отмена, неизвестный ID, ошибка провайдера, отсутствие маршрута без флага и состав СБП-запроса. Секреты магазина, платёж и production не используются. Результаты команд и CI записать в PR после проверки.

Для будущего ограниченного развёртывания: сначала сохранить копию только test bot/feed unit, env и изолированной БД; выполнить миграции только этой БД, если они появятся; проверить `/ready`, feed 200 с действующим доступом без вывода URL и 404 для неверного токена; сравнить срок подписки до/после фиктивного повторного события. При ошибке вернуть тестовые bot/feed файлы и env, перезапустить только эти две тестовые службы. Xray, agent и production не трогать. **Этот PR не требует миграций и не развёрнут.**

## Перед реальными платежами

1. Отдельно подтвердить в кабинете ЮKassa подключение СБП **боевого** магазина. [Официальная документация СБП](https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp) задаёт `payment_method_data.type=sbp`; [официальная документация тестового режима](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing) разрешает проверять в тестовом магазине только карту и ЮMoney.
2. Выбрать безопасный публичный HTTPS-вход на 443/8443 для webhook либо оставить подтверждённый опрос. [Требования ЮKassa к уведомлениям](https://yookassa.ru/developers/using-api/webhooks) исключают текущий 18443.
3. Подготовить отдельный, ещё не реализованный production-адаптер и конфигурацию магазина с новым набором тестов; проверить фискальные чеки, оферту, статус магазина, возвраты, ошибки СБП и политику персональных данных. Боевые реквизиты держать только в защищённом хранилище/переменных окружения, не в Git и не в сообщениях.
4. Проводить реальный платёж и включать продажу только по новому прямому разрешению владельца после изолированного сквозного испытания. Ни один Draft PR не объединять автоматически.
