# Подготовка первого сквозного опыта Telegram → Happ

**Статус:** только ревью и автоматические проверки. В PR №6 добавлены
шаблоны второго, отдельного Xray/агента. Они не устанавливались. Существующие
JustHost:8443 и JustHost:9443, DigitalOcean, Telegram-бот, базы и платежи не
менялись. Ниже указаны проверки, которые нужно завершить **до** отдельного
разрешения на развёртывание.

## Домен, DNS и HTTPS

- В исходниках и доступной пилотной среде не найден установленный
  `SUBSCRIPTION_PUBLIC_URL` или готовый публичный HTTPS ingress для
  `/s/<token>`. В кабинете JustHost среди активных услуг виден только VPS,
  платной услуги домена нет. **Обнаружено выданное хостером имя сервера** в
  зоне `vm.mydomain.zone`; имя не является доменом, принадлежащим KudaVPN.
  Независимый DNS-over-HTTPS ответ Google Public DNS дал A и AAAA,
  совпадающие с IPv4/IPv6 в кабинете VPS; CAA-записей в цепочке не найдено.
  Обычный `dig` на Mac под сторонним VPN возвращал `198.18.4.239` (fake-IP),
  поэтому его ответ не использован как доказательство публичной DNS-записи.
  Сессию DigitalOcean для проверки его DNS открыть не удалось: кабинет
  потребовал вход. Владелец ранее сообщил, что отдельного домена проекта нет.
- **Предпочтительно без покупки для короткого пилота:** использовать выданное
  JustHost FQDN и обычный доверенный сертификат Let's Encrypt на это имя.
  DNS-01 недоступен без управления зоной, зато HTTP-01 возможен, если
  публичный TCP/80 обслужит ACME challenge. После выпуска feed может жить
  на отдельном HTTPS-порту; TCP/443 действующего сервиса не занимать.
  Сначала проверить условия использования и устойчивость выданного hostname,
  реальную занятость 80/18443 на VPS, firewall, staging ACME и импорт URL
  `https://hostname:порт/s/<token>` в Happ. Имя зависит от аренды сервера и
  **не годится как долгосрочный коммерческий бренд-адрес** без дальнейшего
  решения об управляемом проектом домене.
- **Резерв без домена:** доверенный IP-сертификат Let's Encrypt на публичный
  IPv4. Он действует 160 часов, поэтому требует частого автоматического
  продления и reload только новой HTTPS-службы; Certbot 5.4+ поддерживает
  `--ip-address` с `--webroot`. Его применять только если вариант с FQDN не
  прошёл и после отдельного согласования. TCP/80 нужен для HTTP-01;
  TLS-ALPN-01 на 443 не использовать из-за действующего сервиса.
- Минимум для feed: публично доверенный сертификат, совпадающее имя или IP
  в URL, постоянно обновляемый TLS, отдельный приватный токен на пользователя,
  `Cache-Control: no-store`, отсутствие URL в access-логах и аналитике,
  сервер выдачи с доступом **только к изолированной тестовой БД**. Текущий
  compose готовит бота/БД, но публичный HTTPS ingress и отдельный API-процесс
  пока не подключены. Не направлять feed на production PostgreSQL.

Источники: [IP-сертификаты Let's Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability),
[поддержка Certbot и renewal](https://letsencrypt.org/2026/03/11/shorter-certs-certbot),
[формат обновляемой подписки Happ](https://www.happ.su/main/dev-docs/app-management).

## Второй пользователь без изменения 9443

`deploy/pilot-second/` содержит только **шаблоны**: VLESS + TCP + REALITY
с пустым `clients`, отдельные порт-кандидаты 10443 (публичный VPN), 19086
(Xray API на loopback) и 19445 (mTLS агент на loopback). Новый системный
пользователь, каталоги, SQLite аренды, unit/cgroup, REALITY-пара и mTLS CA
отделены от первого пилота. `NODE_AGENT_MAX_USERS=1`; порты 443/8443/9443
явно защищены в окружении агента. Клиентский fingerprint и SNI согласовать
с **новым** REALITY-набором; действующие UUID/ключи не копировать.

Официальный ответ JustHost по заявке
[№986998](https://my.justhost.ru/tickets/view/986998) разрешает публичный
платный VPN, персональные подключения и Xray/VLESS/REALITY/Vision; отдельного
тарифа или согласования не требует. Ограничение скорости определяется
тарифом; при жалобах на злоупотребления сеть могут ограничить. Это не
равнозначно подтверждению, что именно TCP/10443 уже открыт в firewall.

**Живой preflight остаётся блокирующим:** SSH с `StrictHostKeyChecking=yes`
остановился, потому что на этом Mac не закреплён ED25519 host key JustHost.
Ключ нельзя автоматически принять по непроверенному `ssh-keyscan`. Через
доверенную консоль провайдера или другим независимым каналом сначала сверить
fingerprint, затем добавить ключ в `known_hosts`. После этого только чтение:
`ss -lntup` для 80/443/8443/9443/10443/18443/19086/19445, статус служб,
`nft list ruleset`/`ufw status`, настройки сетевого фильтра в кабинете,
свободную RAM/диск и действующий 8443. Выбор портов **условный** до этой
проверки; при коллизии не менять общие правила, а выбрать новые свободные
порты и обновить шаблоны/тесты.

Перед будущей установкой: отдельное разрешение владельца на новые файлы,
службу и точечное открытие 10443 (если требуется); бэкап только новых
компонентов; `xray run -test -c` с новым конфигом; `systemd-analyze verify`;
сверка PID/хеша 8443 и 9443 до/после. При любой ошибке остановить и удалить
только вторую службу; не перезапускать первые две.

## Отдельный тестовый бот через BotFather

1. В Telegram открыть официальный `@BotFather`, отправить `/newbot`, задать
   узнаваемое имя вроде `KudaVPN Test` и свободный username, заканчивающийся
   на `bot`. Не использовать production `@KudaVpnBot`.
2. Сохранить выданный токен **только** в приватном локальном файле с правами
   `0600`; не пересылать в чат, не вставлять в Git, отчёты или командную
   строку, попадающую в историю shell. Владельцу/инженеру достаточно сообщить
   username и числовой bot ID отдельно от токена.
3. При будущем запуске указать путь к приватному файлу и ожидаемый bot ID в
   изолированном compose. Launcher отвергает старый `DATABASE_URL` и токен
   другого бота. Не запускать два poller-процесса с одним токеном.

## Приёмка первого сквозного испытания

1. Получить отдельные разрешения на второй Xray/агент, HTTPS ingress/ACME и
   запуск тестового бота. Проверить чистый `git status`, все секреты вне Git,
   новую пустую PostgreSQL и успешные миграции до `0007`.
2. Проверить доверенный TLS feed и мTLS туннеля к **второму** агенту: health
   положительный с клиентским сертификатом, TLS-рукопожатие без него
   отвергается. Административные API остаются только на loopback. Закрепить
   ровно один ID второго узла в приватной конфигурации шлюза.
3. В тестовом боте зарегистрировать один новый Telegram ID. Отдельный
   операторский harness создаёт фиктивный заказ и подтверждённое событие,
   **без** YooKassa; повтор того же события не добавляет срок. Бот показывает
   одну персональную HTTPS-ссылку лишь после ACK агента.
4. В Happ на Android импортировать эту ссылку, увидеть **новый** узел 10443,
   открыть HTTPS-сайт и YouTube; зафиксировать фактический выходной IP.
   Рабочие профили 8443/9443 и их пользователи не меняются.
5. Повторным фиктивным событием продлить срок: ссылка и UUID остаются теми же.
   Затем дождаться короткого естественного истечения: feed отказывает,
   агент удаляет UUID, активный поток рвётся, новая VLESS-авторизация не
   проходит. После нового фиктивного продления прежняя ссылка работает.
6. Отдельно имитировать недоступность агента: нет ложного ACK отзыва,
   нездоровый узел не выдаётся, операция повторяется при восстановлении.
   Сверить PID/доступность 8443/9443 до и после.

**Остановить опыт** при расхождении БД и агента, ошибке TLS, неожиданном UUID,
потере 8443/9443, публикации секрета или проблеме обновления IP-сертификата.
Откат включает только второй узел, новый HTTPS ingress, тестовый bot/DB и
туннель; никакого удаления production-данных или изменений оплаты.
