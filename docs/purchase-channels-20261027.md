# Покупка KudaVPN: самостоятельный сайт и Telegram Stars

Состояние 27 октября 2026. Продолжение Draft PR [29](https://github.com/Denis-hud-dev/vpn-service/pull/29), без изменений действующего сервера. Последний живой тест оплаты 199 ₽ и единственного продления принят как завершённый; новые платежи не создавались.

## Два независимых канала, одна подписка

| Канал | Способ оплаты | Что уже есть | Что ещё требуется |
|---|---|---|---|
| Самостоятельный сайт, открытый непосредственно в обычном браузере | ЮKassa, RUB; карта, СБП после подтверждения магазина | OIDC, owner sandbox, единый канонический пользователь/заказ/подписка, сохранение UUID/Happ, проверенное продление | Публичный запуск и live отдельно согласуются; СБП в данном sandbox недоступна |
| Покупка внутри Telegram/бота/Mini App | Telegram Stars, XTR | Только отключённый offline-контракт официальных методов | Цены XTR, отдельный TEST-server бот, учёт валюты и привязка тестовой личности, доверенный transport и транзакционная обработка |

[Правила Telegram](https://core.telegram.org/bots/payments-stars#faq) и [условия разработчика §6.2](https://telegram.org/tos/bot-developers#6-2-digital-goods-and-services) требуют Stars для цифровых услуг внутри Telegram; наличие внешнего сайта этого не отменяет. В боте не добавлены RUB-инвойсы, ссылки на оплату, Mini App с внешней кассой, сокращатели или скрытые переходы. Существующий `bot/handlers/subscription.py` уже отключает внешнюю покупку, включая старые callbacks. Самостоятельный сайт не запускается из бота как замена Stars. OIDC подтверждает личность для отдельно открытого сайта, а не служит обходом платёжных правил. Это архитектурное разделение, не индивидуальное одобрение проекта Telegram.

Пользователь сайта по-прежнему определяется только проверенным OIDC-сеансом. Заказ привязан к каноническому User, подписка и UUID прежние. У auth-приложения нет ключа ЮKassa или прав записи в источник: платежи проходят через существующий локальный мост. Вторых пользователей/подписок/платёжных ledger не добавлено.

Для будущего Stars нужен **тот же канонический order/payment/subscription lifecycle**, а не отдельная база покупок. Текущий Payment имеет ограничение RUB и поле amount_kopecks; переносить туда XTR как рубли/копейки нельзя. План: аддитивный price snapshot с currency/amount_minor, неизменяемая версия тарифа и provider/environment, уникальный charge key; совместимость старого RUB-кода сохраняется. Затем обобщается существующее исполнение срока с проверкой провайдера. В этой сессии миграций и такого финансового расширения нет: сначала цены и модель учёта должны быть согласованы.

## Сокращение действий на сайте

Подготовлено в коде, **на сервер не развёрнуто**:

- `/auth/login` с действующим разрешённым cookie сразу возвращает в кабинет; новый state/PKCE-сеанс не создаётся, срок текущего cookie не увеличивается. Истёкший/неверный сеанс требует обычного OIDC. URL user ID и пользовательский redirect не принимаются.
- Опциональный `SITE_DIRECT_CHECKOUT=1` меняет кнопку на «К тестовой оплате ↗». Только после её явного нажатия и ответа backend происходит переход в текущей вкладке на проверенный HTTPS-адрес ЮKassa/ЮMoney. Из цепочки убирается дополнительное нажатие ссылки уже созданного заказа.
- Перед переходом сверяются test flag, RUB, сумма и срок выбранного тарифа; запрещены чужой host, HTTP, userinfo, иной порт и fragment. Reload, status polling, отмена, истечение окна и успешный заказ не перенаправляют на новую оплату.
- После подтверждения и свежей готовности доступа показывается отдельная кнопка Happ на защищённый `/connect`. Во время обновления доступа повторная покупка не предлагается как решение проблемы.
- Флаг выключен по умолчанию и принудительно недоступен при read-only review. Сохранены запасная ссылка провайдера, проверка статуса/backoff и совместимость со старым HTML без новой кнопки.

Целевой путь для действующего сеанса: **тариф → форма ЮKassa → подтверждённая сервером подписка → Happ**. Первый вход добавляет OIDC. Нельзя обещать отсутствие повторного входа после истечения фиксированного часового сеанса. Тарифы остаются 199/499/1790 ₽; финансовая логика не менялась.

Перед включением нового UX на закрытом стенде: проверить CI, сохранить прежний release/env, обновить только сайт, проверить `/ready`, owner-only доступ и UI без создания оплаты. Сначала оставить `SITE_DIRECT_CHECKOUT=0`; затем отдельно включить для владельца и проверить переход. При ошибке вернуть предыдущий сайт/env. В этой сессии это развёртывание не выполнялось, готовый E2E не повторялся.

## Stars: безопасная техническая подготовка

`bot/services/stars_sandbox.py` не импортируется runtime бота, не регистрирует Router, не создаёт Bot/HTTP client, не хранит токен и не выполняет сетевые вызовы или выдачу VPN. По умолчанию выключен; утверждённых тарифов XTR в нём нет. Число 7 в тестах — синтетическая fixture, не предложение клиентам.

Подготовлены типизированные `sendInvoice` (XTR, один LabeledPrice, пустой provider_token, один частный получатель), `answerPreCheckoutQuery` и проверка формы `successful_payment`. Pre-checkout не активирует доступ. Проверяются владелец, сумма и payload, запрещено рекуррентное списание; задержанный успех сохраняет ту же ссылку на заказ. Повторная observation возвращает тот же charge/order, **но это не реализованная транзакционная дедупликация**: её необходимо подключить к общему ledger. Shape validation также не доказывает происхождение события — нужен доверенный update transport. [Bot API](https://core.telegram.org/bots/api#sendinvoice), [платёжный процесс](https://core.telegram.org/bots/payments-stars).

Для настоящего безопасного теста Telegram предоставляет [отдельную TEST-среду](https://core.telegram.org/bots/webapps#using-bots-in-the-test-environment), где нужны отдельные аккаунт и бот; API использует `/bot<token>/test/METHOD`. Установленная aiogram уже содержит официальный `TEST` server template. Обычный @KudaVPN_Test_Bot принадлежит основной среде: название Test не делает Stars фиктивными. Его токен не переиспользовать. Код прототипа не подключён ни к какому transport; фактический test-client и его привязка к TEST появятся только после решения владельца.

Действия владельца перед следующим Stars-этапом:

1. Согласовать тестовые цены в целых XTR для 1/3/12 месяцев; автоматического курса к 199/499/1790 RUB нет.
2. Создать отдельный test-server аккаунт/бот через test-server BotFather. В Telegram macOS официальная инструкция: 10 нажатий на значок Settings, затем ⌘+Add Account; для Telegram Desktop — Settings → Shift+Alt+правый клик Add Account → Test Server. Новая тестовая личность не считается прежним владельцем по совпадению числового ID.
3. После этого подготовить скрытый локальный ввод отдельного токена вне Git; значения в чат не присылать. Согласовать явную привязку тестовой личности к канонической fixture, валютную миграцию только disposable DB и trusted update store. Существующую тестовую подписку не переносить/не дублировать.
4. Проверить paid update → один канонический grant → повтор без второго срока → refund/reconciliation и поддержку `/paysupport` до любого публичного включения. Проверка оплаты не заканчивается на pre-checkout или скриншоте.

## Webhook без вмешательства в VPN

[ЮKassa требует HTTPS443/8443](https://yookassa.ru/developers/using-api/webhooks); текущие20443/18543 для webhook не подходят. Существующие443/8443 заняты VPN. Перестановка Xray, SNI/fallback proxy, port forwarding или правила firewall изменили бы работающий контур и не разрешены. DigitalOcean исключён из текущих изменений.

Без такого изменения возможна отдельная HTTPS-точка443 на другом уже доступном адресе/хосте. Наличие такого ресурса не подтверждено; покупка, DNS и сетевые изменения не выполняются. Предлагаемый first-party ingress не имеет ключа магазина или доступа к БД: ограничивает размер/частоту запросов, сохраняет только event/object ID в durable queue и возвращает200 после записи. Закрытый worker JustHost получает события через исходящее защищённое соединение, принимает только известный order/provider ID и независимо проверяет ЮKassa API; применяется прежняя идемпотентная активация. Не хранить целиком provider payload, контакты/карты/персональные ссылки в relay/logs. Для refund нужна отдельная проверка refund+родительского платежа и транзакционный review.

Точечная проверка JustHost только на чтение подтвердила один публичный IPv4 и один IPv6. `ss -6 -ltnH` показывает wildcard `*:443` и `*:8443`, а не свободный отдельный IPv6 listener. Поэтому использовать этот имеющийся IPv6 для нового443-сервиса без изменения текущего слушателя нельзя. Порты не пробовали занимать, сервисы не останавливали. Другой подтверждённой свободной HTTPS-точки в разрешённой области пока нет.

Надёжность relay, права/ключи, replay/дедупликация, запас очереди и failover требуют тестов до запуска. Ложное уведомление не должно выдавать VPN, а неуспешная запись не должна подтверждаться200. ЮKassa повторяет доставку до24h. Пока ingress не согласован, остаётся работающий polling; его нельзя называть webhook. Для продаж дополнительно нужны сверка потерянных/неоднозначных заказов и возвратов, контроль задержки и operator review. Случайный публичный туннель/неизвестный сторонний relay не предлагается как готовое надёжное решение.

## НПД и что блокирует реальные продажи

Продавец — самозанятый, НПД, без НДС. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics) прямо отделяет квитанцию оплаты от чека: доход регистрируется в «Мой налог», чек передаётся покупателю; автоматическая опция для НПД в ЮKassa недоступна. Интеграция с ФНС не считается готовой. Нельзя включить вместо неё параметры54-ФЗ/НДС для ИП/ООО.

[ФНС](https://npd.nalog.ru/faq/) указывает формирование/передачу в момент расчёта для электронных средств платежа, и иной срок для других безналичных форм; не назначать всем картам/СБП произвольно срок «до9-го числа». До live нужен утверждённый способ передачи: контакт для электронного чека или допустимый QR-сценарий. Один статус в личном кабинете не доказательство доставки. Не собирать телефон/email ради sandbox без необходимости. При возврате требуется корректировка НПД, подтверждение документа и отражение ошибки/доставки в уже подготовленном NPDLedger. Реальная регистрация/передача и частичные возвраты остаются операционными задачами. Для Stars отдельно не подтверждены оценка дохода/момент признания и связь с вознаграждениями — курс RUB не выдумывать; до live нужна согласованная схема учёта.

Оставшиеся решения: Stars цены/TEST-бот и общий currency-aware lifecycle; согласованный webhook ingress либо утверждённая полноценная polling/reconciliation-модель; магазин live/СБП и модерация; НПД-процедура, документы продавца и разрешение на публичные продажи. Рабочие тестовые OAuth/ЮKassa/Happ сохраняются, live и автосписания не включены.
