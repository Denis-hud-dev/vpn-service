## Исправлено без доступа к инфраструктуре

В `bot/services/yookassa_api.py` настоящая HTTP-СБП в тестовом магазине теперь отклоняется до запроса, в том числе при загрузке файлов конфигурации. Старый synthetic SBP payload contract доступен только через injected offline transport. Это не добавляет live-клиент и не разрешает оплату в боте.

HTTP JSON читается полностью по частям с лимитом256KiB; неожиданный MIME/redirect, повреждённый UTF-8/JSON, чрезмерная вложенность и oversized ответ не принимаются. Тексты ошибок общие, тело провайдера не выводится.9 новых regression tests используют fake HTTP session, без обращения к магазину.

Профильный прогон: **160 passed,1 skipped** — платежи/уведомления/повторы/возвраты/сроки/авторизация/реестр и проверка выключенных каналов. Это отдельный локальный skip, не три исторических Xray skip полного CI. Новые серверные/физические Android тесты не заявляются.

### СБП

[Официальный sandbox](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing) допускает карту/ЮMoney; СБП проверяется только в настоящем магазине. Успешный тест карты1503208 **не подтверждает** СБП боевого магазина. Настройки live-магазина в этой работе не читались и не менялись. [ЮKassa о подключении СБП](https://yookassa.ru/sbp/): подключение магазина/договора и СБП совместно с другими способами через Умный платёж/Виджет. Статус конкретного магазина требуется подтвердить отдельно, без передачи ключей в чат.

Будущая выдача СБП должна зависеть от подтверждённой merchant capability. Не показывать её доступной по одному feature flag. API-поле `payment_method_data.type=sbp` и mock payload не доказывают реальную доступность. Финальная реальная проверка — только с отдельным разрешением; настоящих списаний не было.

### Webhook и polling

[ЮKassa требует HTTPS443/8443](https://yookassa.ru/developers/using-api/webhooks), TLS≥1.2. Текущий20443 не подходит;443/8443 уже заняты защищёнными VPN listener, включая wildcard IPv6. Нельзя занять их или поменять общую маршрутизацию под видом настройки сайта.

Варианты: сначала реализовать надёжную исходящую API-сверку без изменений сети; либо отдельно согласовать first-party HTTPS ingress с устойчивой очередью и чтением JustHost наружу. До согласования ingress не создавать и DNS/firewall не менять. Webhook payload — подсказка, не доказательство; независимая проверка статуса/суммы/валюты/metadata и известного заказа обязательна. Поллер остаётся fallback даже при webhook. Покрыть также refund.succeeded, временные ошибки, повтор и потерянный ответ.

### Чеки самозанятого

Продавец уже подтверждён: **НПД, без НДС**; повторно не спрашивать статус. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics) указывает необходимость регистрации дохода в «Моём налоге» и передачи чека покупателю; автоматическая опция ЮKassa для самозанятых сейчас недоступна. Квитанция эквайера, запись `issued` и сообщение об оплате не заменяют настоящий чек.

Для ограниченного пилота нужно выбрать: контролируемая ручная выдача/доставка через «Мой налог» либо подтверждённый уполномоченный партнёр. Зафиксировать сумму до комиссии, дату расчёта, услугу, документ и подтверждение доставки; при возврате — соответствующую корректировку. Не добавлять настройки НДС/кассы ИП/ООО, не автоматизировать вход в «Мой налог» неофициальными средствами. В sandbox нет реального дохода и настоящие чеки не формируются.

## Точная точка продолжения

Следующий технический шаг — проект/тесты durable API reconciliation для платежей и возвратов, используя существующие `PaymentNotificationProcessor` и `TestRefundProcessor`. Покрыть рестарт/повтор/пагинацию/неопределённый POST/терминальный ответ и сохранить канонический UUID. Сеть и рабочие сервисы для этого менять не требуется; включать worker только после отдельной приёмки и backup/rollback.

От владельца перед продажами: подтвердить СБП нужного live-магазина, выбрать процесс чеков НПД, утвердить документы и последующий закрытый пилот нескольких покупателей. Ключи сейчас не запрашиваются. Stars остаются выключенными, не блокируют сайт; внешнюю кассу цифровых услуг из Telegram не включать. Никаких live-платежей до отдельного разрешения и закрытия P0.
