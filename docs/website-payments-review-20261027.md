# Закрытый сайт: подключение тестовых платежей — 27 октября 2026

Основа: Draft PR [29](https://github.com/Denis-hud-dev/vpn-service/pull/29) поверх PR27. Вход Telegram, кабинет, композиция сайта и прежняя персональная ссылка Happ уже проверены владельцем; не переделывались.

## Что добавлено

Существующий PaymentCheckoutService, PaymentNotificationProcessor, версии PILOT_TARIFFS и SubscriptionService переиспользуются через отдельный Unix-only процесс. Web UID проходит SO_PEERCRED, затем применяется единственный owner ID из приватной конфигурации. Поля owner_id, цена, срок и произвольные команды в RPC не принимаются. Из браузера необходим прежний OIDC-сеанс, Origin и CSRF.

Веб-процесс по-прежнему не получает ключи ЮKassa, пароль канонической БД, HMAC Happ, bot token или доступ к агенту. Его собственная БД хранит только авторизацию. Канонические users/subscriptions/payments/UUID не копируются. Существующий экспорт читает прежнюю подписку, историю и токен, без выпуска нового доступа. Новый мост изменяет только существующие тестовые платежи/подписку через прежнюю логику; сам не вызывает Xray/агент и не запускает второй poller. Уже работающий `kudavpn-test-checkout.service` опрашивает pending платежи независимо от браузера. После подтверждения действующий reconciler тестового контура обновляет доступ обычным существующим способом.

Флаг сайта по умолчанию `disabled`; включение только `SITE_PAYMENTS_MODE=owner-sandbox`. Мост принимает только магазин1503208, test_ ключ, каноническую localhost БД `kudavpn_telegram_pilot`, порт сайта20443 и возврат `/account`. Никаких live/SBP/автосписаний, публичного webhook или нового платёжного перехода в Telegram нет.

Тарифы: 1 календарный месяц199 ₽,3 месяца499 ₽,12 месяцев1790 ₽. Версии старых заказов и уже оплаченные сроки не меняются. Продление: add_months(max(текущее окончание, время подтверждения), оплаченные месяцы). Поэтому месяц может отображаться как тариф при большом накопленном остатке; это разные значения.

## Исправления

- Непривязанный pending заказ после сбоя БД при сохранении provider ID больше не заменяется другим заказом после30 минут. Сохраняется исходный ключ идемпотентности. Непривязанные заказы получают приоритет при повторном запросе того же тарифа.
- Повторный POST по слишком старому заказу блокируется до сверки: окно взято23h с запасом относительно документированных24h ЮKassa. Такие неоднозначные случаи не считаются автоматически восстановленными; нужны поиск в магазине по order_id и проверенный GET. История/подписка не меняются наугад.
- Незавершённая оплата восстанавливает URL провайдера через проверенный GET, без нового POST после перезагрузки страницы.
- Браузер повторяет проверку с ограниченным backoff при временной ошибке; при401 останавливается и просит войти заново.
- После confirmed payment сайт ждёт свежий экспорт/готовность прежнего доступа; не предлагает оплатить повторно из-за задержки обновления кабинета.
- Подтверждённый CI timeout Node увеличен5→15s; assertions копирования не менялись.

## Развёртывание и откат

Первая попытка с runtime5297e8a автоматически откатилась на прежний28f9c23: subprocess проверки импортировал `bot` из неверного cwd. Сам мост стартовал без рестартов и штатно остановился при откате. Read-only сайт снова ready; protected baseline совпал. Это не ошибка платежа или VPN. Исправлен cwd и добавлен лёгкий stdlib-only probe настоящего Unix HTTP-запроса; его отдельно проверяет тест из пустого каталога с isolated Python. Ожидание ограничено90s по monotonic, без отключения readiness. Измеренный холодный старт моста потребил12.8 CPU-sec и достиг лимита192MiB; новый изолированный лимит256MiB/50% даёт запас, не меняя ограничений других служб. Повторный запуск допустим только `--resume-rolled-back` с совпавшими сохранёнными code/env/owner/credential/source digest и прежним рабочим сайтом; базовый установщик не перезаписывает backup.

`deploy/website-review/enable_payments.py COMMIT` запускается только из нового проверенного immutable release. Перед изменениями он проверяет старый работающий сайт, сохраняет root-only конфигурацию/старую release-ссылку, pg_dump обеих тестовых БД, проверяет читаемость dump, фиксирует защищённые PID/listeners/config hashes и хеш canonical rows. Ни миграций, ни платежей установщик не создаёт. Новый systemd-процесс имеет отдельный OS UID, sealed credentials, Unix socket0750/без world-доступа, readonly FS, пустой capability set и лимиты памяти/CPU.

Backup: `/var/backups/kudavpn-website-review/20261027-payments`. `rollback.sh` останавливает только новый мост и возвращает прежний рабочий сайт/env; после этого проверяются readiness и защищённый baseline. БД автоматически не восстанавливается поверх возможного нового подтверждённого платежа. При провале readiness установщик выполняет этот откат автоматически. Старый контроллер9443, Monitor, Xray, боты, checkout18543 и feed18443 не перезапускаются.

## Подтверждённые внешние ограничения

Проверено27.10.2026 по первичным источникам:

- [ЮKassa webhook](https://yookassa.ru/developers/using-api/webhooks): HTTPS только443/8443.20443 и18543 не подходят.443/8443 заняты защищённым VPN; нельзя их занимать/менять reverse proxy. Для настоящего webhook потребуется отдельно согласованный ingress. Пока используется существующий polling.
- [Идемпотентность](https://yookassa.ru/developers/using-api/interaction-format): одинаковый ключ и тело в течение24h; после этого повтор может стать новой операцией. Произвольный бесконечный POST retry небезопасен.
- [Тестирование](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing): тестовые деньги. По подтверждению поддержки данного магазина СБП недоступна; принимаем только тестовую карту/ЮMoney.
- [Чеки НПД](https://yookassa.ru/developers/payment-acceptance/receipts/basics): самозанятый должен зарегистрировать доход в «Мой налог» и передать чек покупателю; ЮKassa эту опцию не предоставляет. Квитанция оплаты не заменяет чек. НДС продавца не применяется; настройки54-ФЗ для ИП/ООО не добавлялись. Существующий NPDLedger — реестр обязательств/статусов, не подключённый сервис ФНС. Для sandbox показано `test_not_required`, реальный чек не выдумывается.
- [Telegram Stars](https://core.telegram.org/bots/payments-stars#faq): цифровые услуги внутри Telegram требуют Stars независимо от наличия внешнего сайта. Внешняя продажа остаётся самостоятельным сайтом; ссылки обхода оплаты внутри бота/Mini App не добавлялись.

Для реальных продаж остаются: согласованный webhook ingress/повторная доставка и refund reconciliation; боевой магазин и подтверждение СБП; процедура НПД-чека/доставки/корректировки; согласование документов и данных продавца; recovery неоднозначных неподтверждённых созданий; отдельный план открытия доступа покупателям и явное разрешение владельца. Закрытый owner sandbox нельзя считать публично готовым коммерческим сервисом.
