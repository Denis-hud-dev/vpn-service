# Ограниченная приёмка управляемого VPN-узла KudaVPN

Документ описывает **будущее** испытание после отдельного разрешения владельца.
Код PR №6 не установлен на JustHost или DigitalOcean. Работающий статический
JustHost TCP/8443 и DigitalOcean TCP/443 не используются управляющим агентом.

## Что запускается отдельно

- Новый Xray-процесс с одним VLESS + TCP + REALITY + Vision inbound на заранее
  проверенном **свободном** порту. В конфигурации `settings.clients: []`, нет
  статических пользователей и нет fallback. Новый REALITY private key и
  сертификаты управления хранятся вне Git. Нельзя копировать тестовый UUID с
  рабочего 8443. `XRAY_CONFIG` доступен только отдельному сервисному пользователю
  (`0600`); `XRAY_API_ADDRESS` — только `127.0.0.1`.
- Агент запускает этот Xray дочерним процессом в **той же** службе systemd.
  Пример unit для ревью (пути и интерфейс определить на площадке):

  ```ini
  [Unit]
  Description=KudaVPN isolated managed node
  After=network-online.target
  Wants=network-online.target

  [Service]
  Type=simple
  User=kudavpn-node
  Group=kudavpn-node
  WorkingDirectory=/opt/kudavpn-node
  EnvironmentFile=/etc/kudavpn-node/agent.env
  ExecStart=/opt/kudavpn-node/venv/bin/python -m bot.node_agent.main
  Restart=on-failure
  RestartSec=3s
  KillMode=control-group
  TimeoutStopSec=10s
  NoNewPrivileges=yes
  ProtectSystem=strict
  ProtectHome=yes
  ReadWritePaths=/var/lib/kudavpn-node

  [Install]
  WantedBy=multi-user.target
  ```

  До запуска проверить `systemd-analyze verify`, расположение бинарника и
  права, затем `xray run -test -c` для **новой** конфигурации. Переменные в
  `/etc/kudavpn-node/agent.env` — только для нового сервиса: `NODE_AGENT_STATE`,
  `XRAY_BINARY`, `XRAY_CONFIG`, `XRAY_API_ADDRESS`, `XRAY_INBOUND_TAG`,
  `XRAY_INBOUND_PORT`, `NODE_AGENT_CERT`, `NODE_AGENT_KEY`,
  `NODE_AGENT_CLIENT_CA`; при необходимости `NODE_AGENT_LISTEN` и
  `NODE_AGENT_PORT`. Файл `0600`, каталог `0700`, отдельный CA и mTLS.
  Ограничить маршрут к порту агента только центральным управляющим сервером;
  порт Xray API наружу не открывать. Не переопределять защищённые порты 443/8443.

## Один тестовый пользователь, без настоящей оплаты

1. Получить отдельное разрешение на установку **только нового** сервиса;
   проверить копию ответа JustHost №986998, действующие порты/правила, сделать
   бэкап нового состояния и записать команды отката. Никаких изменений в
   действующих службах.
2. В изолированной тестовой БД создать одного фиктивного пользователя и
   имитировать подтверждённую оплату. Управляющий сервис выдаёт персональный
   UUID с короткой арендой, затем HTTPS-ссылку Happ. Убедиться, что UUID
   отсутствует в журналах и отличается от рабочего 8443.
3. Импортировать ссылку на Android, проверить через домашний Wi-Fi реальный
   HTTPS/YouTube и внешний IP. Статус «подключено» сам по себе не считается
   успехом. Продлить тестовый срок и убедиться, что ссылка/UUID сохранились,
   а срок аренды на узле обновился.
4. Открыть длинное HTTPS-соединение через тестовый узел. Заблокировать
   **только этого** фиктивного пользователя. Требуемый результат: feed сразу
   отказывает; центральная БД фиксирует намерение отзыва; агент снимает UUID,
   перезапускает лишь свой Xray; открытый поток обрывается; новая попытка
   VLESS не авторизуется; `revocation_confirmed=true` появляется только после
   успешного применения. Сверить PID старого/нового управляемого процесса и
   неизменный PID/состояние рабочего 8443.
5. Повторить отдельно с естественным истечением срока, отзывом ссылки и
   потерей связи с центром: при отключённом центре UUID должен исчезнуть не
   позднее локального TTL 120 секунд плюс цикл сверки 5 секунд. Затем
   восстановить связь и проверить версионное согласование. Убить **только
   новый** агент в испытании: его Xray-процесс и порт должны исчезнуть вместе
   с группой systemd; при рестарте возвращаются лишь неистёкшие аренды.
6. Смоделировать отказ применения отзыва: статус `503`, узел нездоров,
   `revocation_confirmed=false`, повторная попытка после восстановления.
   Настроить оповещения по ошибкам согласования, нездоровому узлу и зависшим
   неподтверждённым отзывам. Без этих проверок платных пользователей не
   переводить.

## Откат

Остановить только новую службу и убедиться, что её Xray-порт закрыт. Не
удалять запись о неподтверждённом отзыве до сверки. Выключить новый узел из
тестовой выдачи, сохранить обезличенные журналы, восстановить лишь файлы и БД
этого узла при необходимости. Рабочий 8443 и управляющий DigitalOcean остаются
без изменений. Перезапуск общего Xray и откат миграции на работающей БД не
входят в этот сценарий.

## Граница готовности

Локальные тесты проверяют версионные аренды, перезапуск дочернего процесса,
удаление/восстановление UUID и отсутствие ACK при ошибке. Они не доказывают
приёмку systemd, сетевую стабильность Happ и фактическое размыкание реального
туннеля на JustHost. До испытания узел и оплата остаются неактивными.

## Точный пакет для одного пилотного пользователя (подготовлен, не установлен)

Файлы `deploy/pilot/xray-9443.json.template`, `agent.env.template` и
`kudavpn-pilot-node.service` задают **кандидат** TCP/9443, локальный Xray API
`127.0.0.1:19085` и локальный mTLS API агента `127.0.0.1:19443`. Это не
готовые секреты: REALITY private key, short ID, сертификаты и ключи надо
создать заново на узле и оставить в `/etc/kudavpn-pilot` с правами `0700/0600`.
`NODE_AGENT_MAX_USERS=1` действует и при восстановлении сохранённых аренд:
лишние активные аренды должны остановить новый узел. Порт 9443 пока **не
проверен** у JustHost и не открыт. Если он занят или запрещён, остановиться,
не менять firewall без отдельного согласования.

Порядок испытания после отдельного разрешения владельца:

| Шаг | Действие | Ожидаемый результат; иначе остановка |
| --- | --- | --- |
| 0 | Только чтение: записать имя/PID/cgroup/хеш конфига и состояние статического 8443, занятые 9443/19085/19443, действующие правила firewall и лимиты VPS. Проверить полный ответ JustHost №986998 и срок/условия тарифа. | 8443 исправен, новые порты свободны, тестовый вход разрешён. Любая неопределённость о разделении процессов или правилах — остановка. |
| 1 | Подготовить **только новые** каталог, пользователя, отдельный Xray-бинарник фиксированной версии, конфиг, локальную SQLite и сертификаты. Использовать отдельный systemd unit и cgroup; не копировать UUID/ключи 8443. | Шаблоны заполнены вне Git; один inbound с пустым `clients`, API только loopback, `NODE_AGENT_MAX_USERS=1`; `systemd-analyze verify`, локальный валидатор и `xray run -test -c` успешны. Иначе новый сервис не запускать. |
| 2 | Запустить новый unit. Проверить его PID/cgroup, пустой `inbounduser`, локальную mTLS-проверку, прослушивание 9443 и доступность TCP/9443 извне. Управление вести через временный SSH-туннель к `127.0.0.1:19443`; управляющий порт не публиковать. | Статический 8443 имеет прежний PID/хеш и принимает трафик. Отказ, коллизия порта, выход API наружу или изменение 8443 — немедленная остановка и откат нового unit. |
| 3 | В отдельной тестовой БД без реальных клиентов имитировать оплаченный заказ **одного** пользователя, выдать один новый UUID и короткую аренду. Проверить idempotency повторного события. | В агенте ровно один UUID; чужих UUID нет. Второй UUID отклоняется; повтор платежа не продлевает срок. Нарушение — остановка. |
| 4 | При наличии отдельного доверенного HTTPS-адреса выдать персональную Happ-ссылку, импортировать её на Android, проверить HTTPS/YouTube и выходной IP через домашний Wi-Fi. При отсутствии HTTPS-адреса допустима только проверка отдельным ручным тестовым профилем: этот шаг **не** считается приёмкой подписки. | Данные реально проходят через 9443. Статус «подключено»/ping без HTTP-ответа недостаточен. Ошибка подключения — остановка для анализа, без изменений 8443. |
| 5 | Продлить тестовую аренду без смены UUID/ссылки. Затем открыть долгий тестовый поток и заблокировать пользователя. После этого отдельно проверить явный отзыв и естественное истечение. | Срок растёт один раз; feed отказывает после блокировки; API больше не видит UUID, новый вход запрещён, старый поток закрыт после перезапуска **только дочернего** Xray; ACK отзыва появляется лишь после проверки. Проверить PID/cgroup и трафик статического 8443 до/после. Иначе остановка. |
| 6 | На тестовом управлении имитировать потерю связи с центром и отказ операции; затем восстановить. | UUID исчезает не позже аренды 120 с + цикла 5 с; при ошибке ACK отсутствует, узел нездоров, после восстановления согласование возвращается. Если нельзя доказать фактический отзыв — пилот не принят. |
| 7 | Остановить только новый unit и SSH-туннель; проверить закрытие 9443 и 19085, отсутствие дочернего Xray. | 8443 и DigitalOcean продолжают работать с прежними настройками. Сохранить только обезличенные результаты, секреты не выводить. |

Немедленная остановка на любом шаге: меняется PID/хеш/доступность 8443;
управляемый процесс или ключи разделены со статическим; больше одного активного
UUID; mTLS или loopback-ограничение не соблюдены; отзыв подтверждён центром,
но UUID/сеанс остаётся; секрет попадает в журнал; превышены безопасные
ресурсы VPS; зависло согласование. Откат — исключить **только пилотный** узел
из тестовой выдачи, `stop/disable` только нового unit, закрыть только новый
порт по отдельно согласованному правилу, сохранить приватное состояние для
разбора. Восстановление — исправить причину, снова проверить пустой старт и
лишь затем включить новый unit; рабочий 8443 никогда не перезапускать.

Важная граница изоляции: на пилоте есть один пользователь, поэтому перезапуск
его дочернего Xray для разрыва туннеля не затрагивает других клиентов.
В будущем на многопользовательском управляемом узле такой отзыв кратко
разорвёт сеансы **всех пользователей этого узла**; до массового запуска нужна
отдельная стратегия с меньшей областью отказа или принятие этой цены.
