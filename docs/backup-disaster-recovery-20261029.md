## Расписания, ресурсы и права

- На обоих хостах среди активных timers и обследованных cron не обнаружено задания backup PostgreSQL/KudaVPN. `dpkg-db-backup.timer` резервирует пакетную БД ОС, не PostgreSQL.
- На JustHost `pg_basebackup@.timer` существует как **disabled template**, активного instance не найдено. Само наличие шаблона не означает работающий backup.
- `kudavpn-website-export.timer` обновляет рабочий snapshot/read model сайта; он не создаёт независимую историю восстановления. Monitor collector также не заменяет backup.
- DO: свободно77 652 774 912 B (**72.32 GiB**), занято6%; RAM available~3 031 MiB. JustHost: свободно15 914 254 336 B (**14.82 GiB**), занято24%. Для текущих небольших дампов место есть; размер полноценного encrypted runtime/image-комплекта ещё не измерен.
- Все27 дампов0600; четыре основных JH-корня и DO backup-корни0700. Текущие JH Xray-файлы0640, website/payment secrets0600, приватные state-каталоги0700 (export root0750, read model0640). Внешнюю общедоступность этих файлов не обнаружили.
- root SSH/локальная PostgreSQL-авторизация позволяют читать источники; это не повод давать будущему uploader полный root. age/restic/borg не установлены на обследованных хостах, gpg есть. Установка новых инструментов сейчас не выполнялась.

DO bot/PG/Xray остались running с теми же StartedAt, что до аудита. JustHost bot/site/payment bridge/Monitor/Xray active; даты их запуска предшествуют аудиту. Старый controller unit числится failed/не запущен — это ранее остановленный контур9443, не новая авария; не включать его при восстановлении. Аудит не перезапускал службы и не менял VPN-порты.

## Что обязательно резервировать

| Данные | Источник и смысл |
|---|---|
| Пользователи, подписки, срок/статус/тариф, платежи/заказы, уникальные provider IDs и признак активации | Все таблицы **фактической канонической БД**, её sequences, constraints/indexes и migration revision; не только старые семь таблиц |
| UUID, node_access, токены HTTPS-подписки, история, уведомления | Каноническая БД JustHost; восстановить вместе с подписочными signing/HMAC secrets и Xray private keys, чтобы сохранить Happ |
| Web identity, auth/НПД-реестр и события | Существующая website DB0009; будущая0010 не считается уже применённой. Сессии допустимо отозвать и пройти OAuth заново |
| Приватные SQLite и очереди | onboarding.sqlite, checkout sessions, pilot leases; Monitor state/token/peer config для DR-комплекта. Копировать SQLite через backup API, не обычным cp работающего WAL-файла |
| Секреты и конфигурации | Реально используемые env/payment/OIDC/feed/TLS/REALITY configs, PostgreSQL roles/globals и ACL. Только зашифрованно; значение токена/UUID при переносе не менять |
| Runtime и инфраструктура | Точный deployed source/image digest, локально собранный Docker image, compose, systemd units/drop-ins, permissions/UID/GID, enable/disable state, certificate renewal, DNS/firewall/listener inventory |
| Производные файлы | website export/read model можно пересобрать из канонической БД; он не заменяет её. Логи нужны в разумном объёме, с redaction и отдельной retention |

Не копировать активный PGDATA обычным tar как основной PostgreSQL backup. Логический dump одной БД не содержит всех глобальных ролей PostgreSQL и всех файлов приложения.

## Предлагаемая схема — ещё НЕ установлена

1. **Ежедневно, например03:15 UTC**, отдельный systemd oneshot+timer с Persistent=true; backup после перезагрузки должен наверстать пропуск. Фиксировать фактическую live-БД из конфигурации, а не полагаться на начальный POSTGRES_DB. Отдельные logical custom-format dumps DO live DB, JH canonical и website DB, плюс encrypted globals/role map. Согласованный read-only snapshot, один поток, ограничение времени ожидания блокировок/нагрузки и конечное число повторов. Не блокировать DDL бесконечно.
2. **Шифровать до записи и передачи**: pg_dump/config stream → age public recipient → уникальный .partial; pipefail, umask077. Только после успешного завершения и проверки ciphertext checksum присваивать ready-имя. Приватного ключа расшифровки на исходном VPS нет. Владелец хранит его в защищённом хранилище и независимой офлайн-копии; до запуска требуется проверка обеих recovery-копий.
3. **Offsite без нового VPS**: DO encrypted dumps/configs → выделенный ограниченный получатель на существующем JustHost; JH → аналогичный получатель на DO. Это добавление backup-файлов/учётных записей на действующие серверы и требует отдельного разрешения. Uploader может только создать новый объект; не может читать, переписывать, удалять предыдущие. Отдельная административная учётная запись выполняет retention. Не использовать взаимный полный root-доступ как механизм резервирования.
4. Третья копия — зашифрованный экспорт на Mac/офлайн-диск владельца. Две VPS-копии защищают от потери одного провайдера, но не от компрометации обеих админских учётных записей; для более сильной защиты понадобится отдельно согласованное immutable/offline-хранилище.
5. **Версии: 14 ежедневных + 8 еженедельных + 6 ежемесячных**, неизменяемые имена UTC+host+DB+runID. Promotion/pruning только после offsite ACK; всегда сохранять последнюю независимо проверенную рабочую копию. Нельзя поверх единственного good backup записывать новый. Ошибочная/нулевая копия не проходит promotion. Retention/key-rotation не выполнять без сохранения ключей старых копий.
6. Проверки каждого запуска: exit status, точная DB/schema, состав таблиц, ненулевой разумный размер, ciphertext SHA256, offsite ACK, время последнего успеха **по каждой БД**. Один общий зелёный индикатор не должен скрыть пропуск website DB. Ошибка, отсутствие места, недоступность offsite и давность>26ч → owner-only deduplicated alert; recovery после подтверждённого успеха. Присоединить эти факты к Monitor только отдельным согласованным изменением, **нынешний Monitor не менялся**.
7. **Ежемесячная изолированная репетиция**, дополнительно после смены PG major/схемы/ключей: расшифровать и восстановить выбранную offsite-версию, проверить данные и конфигурации. Успех pg_restore/decode не равен успешному восстановлению сервиса. Хранить redacted протокол и измеренное время.
8. **Snapshots**: еженедельно и перед согласованными обновлениями, несколько поколений. Платные DO snapshots/backups включать только после выбора владельцем бюджета; snapshots дополняют дампы и не гарантируют согласованность нескольких БД/SQLite. Если нужна остановка для согласованного image — отдельное окно, не выполнять автоматически над рабочим VPN.
9. Целевой RPO ежедневного задания≤24ч, RTO пока **не измерен**. Плановый ориентир2–4ч подтвердить репетицией. Перед реальными продажами рассмотреть хотя бы4-часовые logical copies либо отдельно спроектированный WAL/PITR: потери суток финансовых данных слишком велики. Настройку WAL/replication slots/портов этим аудитом не разрешать.

Первоначально можно выделить1 GiB под logical/config versions на каждом текущем сервере, затем измерить реальные размеры и growth. Полные images/releases хранить отдельно по релизам и учитывать их размер. Сохранять запас диска≥20% и место под крупнейший архив/репетицию; не расходовать всё свободное место на retention.

## Процедура восстановления — подготовлена, НЕ выполнялась

1. Зафиксировать инцидент, выбрать требуемый UTC recovery point, сохранить неисправные данные для анализа. Не откатывать живую БД поверх новых платежей. При реальной аварии сначала согласовать переключение и исключить одновременную запись двух экземпляров.
2. Получить offsite encrypted archive, manifest и ключ владельца. Проверить ciphertext SHA256, расшифровку, provenance и каталог pg_restore. Хеш, лежащий рядом с архивом под тем же root, выявляет случайное повреждение, но не защищает от злонамеренной подмены обоих; нужен отдельно защищённый manifest.
3. На **отдельной машине/в изолированном контейнере**, PostgreSQL16 той же совместимой версии: новая БД/volume, network none либо отдельная lab-сеть, лимиты RAM/CPU/disk. Никаких рабочих volumes, production DSN, реальных bot polling, API-write/webhook или открытых VPN-портов. SQL дамп может исполнять код — работать только с доверенным источником и изоляцией.
4. Восстановить роли/владельцев в lab либо согласованный role map, затем pg_restore с --exit-on-error --single-transaction --no-owner --no-privileges в **новую lab-БД**. ACL восстановить из защищённого manifest отдельно. Проверить revision, полный состав таблиц, constraints/indexes/sequences, counts/row hashes относительно manifest, связность user→payment→subscription, однократность grant и сохранение UUID/token. Не выводить содержимое строк в протокол.
5. DO: выбирать live DB из DSN, не старую staging. JH: canonical0008 восстанавливается как единственный источник доступа; website0009 — существующее auth/НПД-состояние. Dumps разных БД не являются одной атомарной точкой: требуются reconciliation заказов/очередей и проверка связей. При расхождении запретить новую выдачу до разбора; возврат не должен автоматически уменьшать срок. Платежи сверять API GET, не повторять списания.
6. Бота собрать из **точной рабочей версии**, вернуть его env/units/private SQLite с прежними правами. На DO image ba2f0f6a3daf5400; на JH TEST bot UI-overlay707e130cec22 поверх прежнего backend, website0d45896c9317 и shared bridgefaca30b. Не запускать полный новый PR29/schema0010 вместо старого сервиса. Offline handler/readiness checks выполнять без реального polling; не создавать второго потребителя токена.
7. Вернуть Xray/TLS/REALITY/feed/HMAC configs в lab, проверить синтаксис тем же binary (`xray run -test`), ключевые связи с DB и прежние UUID/URLs сравнением в памяти. Не стартовать Xray на рабочих портах. Учесть права владельцев сертификатов, восстановление домена/сертификата; provider-hostname может зависеть от прежней VM, перенос адреса отдельно согласовывается.
8. Полный DR при реальном инциденте: согласовать final delta/cutover, оградить старую запись, затем по одному разрешать DB→backend→feed/site→единственный bot polling. Переключение DNS/сети/публичных VPN-портов требует отдельного плана и разрешения. Не включать старый controller9443. Monitor восстанавливать с прежними owner-only настройками без повторного аварийного спама.
9. Проверить expiry/tariff/единственное продление, старую персональную HTTPS-подписку и Happ. Автоматического сброса UUID, срока и заказов быть не должно. Измерить время и задокументировать PASS/FAIL. Откат самого приложения не должен автоматически восстанавливать старый dump поверх более новых событий.

Существующий `scripts/verify_backup.py` сейчас **не запускать вслепую на production**: он создаёт plaintext dump и временный контейнер на том же Docker host, жёстко ожидает семь таблиц/revision0002 и использует POSTGRES_DB для pg_dump, хотя актуальный bot DSN указывает другую live DB. Для регулярной системы/JustHost нужна отдельная адаптация к настоящему DSN, полному schema inventory, encryption и внешней restore-lab. Старые UI rollback.sh переключают приложение, а не являются полным DR-процессом БД.

## Риски и порядок действий, требующих разрешения

1. **Высокий:** на DO последняя найденная logical copy19 дней назад; snapshot ещё старше актуального deployment. Зафиксировать свежий consistent backup и независимую offsite-копию после разрешения.
2. **Высокий:** локальные файлы могут погибнуть вместе с VPS; нет подтверждённого ежедневного расписания, end-to-end offsite/restore monitoring и recovery key custody.
3. **Высокий:** полный актуальный комплект runtime/конфигураций/ролей не доказан; корректный DB restore без feed secrets/REALITY/UUID/configs не сохранит Happ.
4. **Средний:** plaintext archives под root0700/0600 защищены файловыми правами, но доступны при компрометации root. Запретить экспорт незашифрованного в Git/облако.
5. До внедрения согласовать: место хранения и retention; владение ключами; backup service/role/ограниченные SSH получатели на обоих серверах; свежие dump/config captures; безопасную restore-lab; owner-alert интеграцию Monitor; отдельный бюджет DO images. Любые перезапуски, изменение VPN/портов и реальное переключение — отдельное разрешение, не часть установки backup.

## Дополнительная стоимость

По DO API нынешний Droplet стоит$24/месяц; snapshot2.29 GB по$0.06/GB≈**$0.14/месяц уже существует**, это не новая расходная статья.

- Encrypted logical copies между существующими VPS + имеющийся Mac/диск: ориентир **$0 дополнительных облачных услуг/месяц** при текущем небольшом объёме и в пределах включённого трафика. Работу/новый физический диск/рост хранения оценивать отдельно.
- Пример четырёх **дополнительных** snapshots по3 GB: 4×3×$0.06=**$0.72/месяц дополнительно**. Будущий фактический размер не равен гарантированно нынешним2.29 GB.
- Альтернатива ручным DO snapshots: basic weekly20% от$24 = **+$4.80/месяц**; daily30% = **+$7.20/месяц**. Это варианты, а не обязательная сумма всех опций.
- У DO есть usage-based планы: weekly$0.04/GiB-month, daily$0.03/GiB-month и более частые. Точная сумма зависит от всех удерживаемых restorable versions и retention; не считать стоимость одной версии ценой всего архива.
- Ничего из перечисленного не подключено и не куплено.

Источники, проверены29 октября2026: [DO backup pricing](https://docs.digitalocean.com/products/backups/details/pricing/), [DO snapshot pricing](https://docs.digitalocean.com/products/snapshots/details/pricing/), [PostgreSQL logical backup](https://www.postgresql.org/docs/16/backup-dump.html).
