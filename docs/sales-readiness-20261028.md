## Исправления

1. PaymentNotificationProcessor теперь сравнивает metadata.order_id с **точно тем** canonical Payment.id, который найден по provider_payment_id. Прежде существование ID проверялось, но metadata могли указать другой unbound pending order с той же суммой. Добавлен regression: чужой заказ не получает grant, обе оплаты pending, чужой provider ID не присваивается.
2. Решение владельца от28октября: **ручной разбор возврата, срок автоматически не уменьшать**. TestRefundProcessor после проверенного succeeded refund записывает review, не изменяя expiry/status подписки/UUID/grant. Старый автоматический rollback доступа удалён. Полный/частичный/ранний возврат, повторные события и прежнее Happ-подключение проверены.
3. В тестовом checkout подключён review gate к PaymentNotificationProcessor: если возврат уже подтверждён, но grant ещё не был выдан, поздний payment hint не активирует доступ до ручного решения. Reconciler не выдаёт новый grant только ради обработки refund. Уже выданный доступ не отзывается; повтор payment не добавляет срок. Это защита подготовленного тестового пути, **не** доказательство атомарности через все действующие сервисы (см. блокер общего журнала).
4. Добавлены `/docs/offer`, `/docs/seller`, `/docs/payments`; ссылки помечены черновиками, реальных ФИО/ИНН/адреса/email не выдумывали. Действующие terms дополнены утверждённым правилом ручного разбора. Публичный запуск и правовой акцепт этими файлами не включаются.

## НПД и «Мой налог»

Владелец — самозанятый на НПД, НДС не применяется; повторно не спрашивать статус и не использовать настройки НДС для ИП/ООО. [ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics) прямо разделяет квитанцию провайдера и налоговый чек: самозанятый регистрирует доход в «Моём налоге» и передаёт сформированный документ клиенту; автоматическая опция для этого в ЮKassa недоступна. Заполнение `receipt` для54-ФЗ не подменяет этот процесс.

По [ФНС](https://npd.nalog.ru/faq/) при наличных/электронных средствах платежа чек формируется и передаётся в момент расчёта. Исключение до9-го числа следующего месяца относится к другим формам расчёта и не является универсальной отсрочкой для любого безнала. Тип расчёта и договорный процесс нужно подтвердить для конкретной схемы приёма. При возврате ФНС предусматривает корректировку с основанием; это отдельный процесс от возврата ЮKassa и от изменения VPN-доступа.

Владелец должен согласовать: ручной «Мой налог» либо подтверждённого уполномоченного партнёра, ответственного за формирование, канал доставки и минимально необходимые контакты, контроль сроков/ошибок, корректировку при полном/частичном возврате. До реальных регистрационного документа и доставки статусы issued/delivered не выставляются. Ключи/пароли «Моего налога» в чат не нужны. Не считать отметку оператора или квитанцию достаточным подтверждением без реального документа.

## Конкретные действия в ЮKassa — до включения денег

- В нужном **рабочем** магазине проверить статус договора/подключения, соответствие самостоятельного сайта и описания собственной VPN-услуги. Поддержка СБП уже подтверждена; требуется фактический статус метода этого магазина, а не повторный sandbox-тест.
- Проверить карту и СБП в доступных способах/Умном платеже, сценарий возврата и необходимые настройки аккаунта. Автосписания не включать. Sandbox1503208 оставлять отдельным.
- Выбрать транспорт: сначала закрыто испытать устойчивую исходящую API-сверку без изменения сети либо отдельно согласовать HTTPS ingress. Для Basic Auth webhook настраивается в «Интеграция → HTTP-уведомления», события payment.succeeded/payment.canceled/refund.succeeded (waiting_for_capture только если нужен двухстадийный сценарий). [Требования ЮKassa](https://yookassa.ru/developers/using-api/webhooks):443/8443, TLS≥1.2. Не указывать нынешний20443 и не занимать VPN-порты.
- Боевые shopId/secret пока не требуются. После отдельного разрешения — только private env/systemd credentials внеGit с минимальными правами, отдельный environment и выключенный приём новых заказов до приёмки. В этой сессии ключи не читались/не заменялись.

## Порядок оставшихся работ

P0: единый canonical refund-review/НПД workflow и операторская процедура (срок не режется автоматически); безопасная проверка межпроцессных гонок/поздних событий/сбоев. Затем закрытая приёмка уже подготовленного reconciliation без смены сети, наблюдаемость задержек и replay/restore. Это самый важный следующий технический шаг.

Параллельно владелец утверждает НПД-процесс и доставку, реквизиты/контакты, оферту/политику/оплату/возвраты; нужно проверить действительный путь обработки/место хранения данных и необходимые правовые действия до публикации, а не придумывать их в черновике. После этого — multi-user staging, isolated live-adapter и согласованная минимальная live-приёмка карты/СБП/возврата/НПД-чека. До отдельного разрешения реальные продажи блокированы.

Telegram Stars не используем, переходов из бота на внешнюю оплату цифровой услуги не добавлено. Сайт остаётся независимым каналом.
