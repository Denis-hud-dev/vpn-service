# KudaVPN Support — первая отдельная версия


**Текущая подготовка после создания бота и группы:** [закрытый запуск и безопасное определение ID](support-prelaunch-20261031.md). Для первого закрытого теста использовать новый `setup-support.command prepare/collect`: он не требует заранее знать ID. Прежний ручной `setup_config` ниже остаётся для явно заданных реквизитов; он не запускает бот, но не заменяет проверку идентичности группы.

Статус: подготовлено в ветке PR #29, **не развёрнуто**. Ни одного запроса к рабочим серверам, Bot API или базам для этой задачи не выполнялось. Работающие боты и службы не менялись.

## Архитектура и границы

- Отдельное приложение: `python -m support_bot.main`, Python + существующий aiogram 3.31.0.
- Отдельные токен, username, пользователь ОС, каталог состояния и systemd unit. Переменные `BOT_TOKEN`, `DATABASE_URL` существующих приложений не используются.
- Переиспользуются только публичный реестр настоящих ID `bot/premium_emoji.py` и фильтр безопасных журналов `bot/observability.py`. Рабочие обработчики, платёжные сервисы и классы, изменяющие подписки, не вызываются.
- Собственная SQLite-база `support.sqlite3`, WAL, foreign keys, транзакции. Миграция v001 — в `support_bot/migrations/`; проектный Alembic к ней не относится. Имя, application_id, версия и права проверяются. Чужая база не мигрируется.
- При первом запуске база привязывается к ID именно нового бота и закрытой группе операторов. Смена бота/группы с той же базой блокируется: нельзя незаметно использовать чужие `file_id` или отправлять прежнюю очередь в другой чат.
- В этой базе **нет** копий пользователей KudaVPN, подписок, UUID, HTTPS-профилей или платежей. Telegram ID в обращении — автор сообщения, а не самостоятельно заявленный ID из текста/URL.
- Сеть используется только будущим запущенным экземпляром для Telegram Bot API. Публичный порт, webhook, VPN-клиент и SSH не нужны. Сейчас ничего не запускается.

## Интерфейс

Главный экран: «Подключение», «Подписка и оплата», «Проблемы с VPN», «Устройства», «Серверы», «Связаться с поддержкой»; дополнительно «Мои обращения» и «Диагностика». Вложенные экраны имеют «Назад»/«Главное меню».

26 вопросов охватывают Android/iPhone/Windows/macOS, установку Happ, импорт и QR, тарифы/продление/оплату/возвраты, сетевые проблемы, устройства и серверы. После каждого ответа есть «Проблема решена» и «Нужна помощь оператора». Пробный период, реферальные бонусы, лимит устройств и гарантированная скорость не обещаются. Возврат — ручной разбор, срок автоматически не уменьшается. Цены 199 / 499 / 1790 ₽ сверяются тестом с существующим каталогом.

Бот не принимает платежи и не содержит ссылки на внешнюю оплату. Логика ЮKassa и Happ не меняется. Реальные продажи в базе знаний не объявляются включёнными.

Фирменные иконки используют существующие ID `KudaVPNPremium`, без новых ассетов. `SUPPORT_CUSTOM_EMOJI=1` включает официальное `icon_custom_emoji_id` в кнопках. По умолчанию выключено до проверки прав нового бота; при явном отказе API из-за custom emoji предусмотрена повторная отправка с Unicode-значком. Сетевой тайм-аут не считается отказом emoji и не вызывает немедленного повторного запроса.

Обычная навигация создаёт новый экран и удаляет **только предыдущий сохранённый навигационный экран в том же приватном чате**. Если удаление запрещено, бот пытается снять старую клавиатуру. Ошибки очистки не мешают следующему переходу. Важные сообщения обращений, ответы, вложения и пользовательские сообщения не удаляются. `/start` возвращает меню и сбрасывает только черновой режим ввода, не обращения. Повторного баннера нет: новый бот не копирует welcome-сценарий основного приложения.

## Обращения и права

Номер `KS-000001` формируется из постоянного AUTOINCREMENT. Хранятся автор, категория/вопрос, описание, статусы, назначенный оператор, даты и история. Статусы: новое → в работе → ожидает пользователя → решено/закрыто. Новое дополнение переводит ожидающее обращение обратно в работу (или в новое, если оператор ещё не назначен).

Пользователь выбирает вопрос → «Нужна помощь оператора» либо общий контакт, отправляет текст/скриншот. Доступны последние 10 обращений, статус, последние 8 записей истории, дополнение и закрытие. Для дополнения после возврата в меню нужно открыть обращение и нажать «Дополнить». Уведомления содержат кнопку открытия обращения.

Вложения: фото и документы с MIME PNG/JPEG/WEBP до 10 МБ; сохраняются `file_id`, но не скачивается содержимое и не открываются присланные URL. Текст до 3000 символов; со скриншотом — до 700, чтобы служебная подпись укладывалась в Telegram caption. Пользователь должен скрыть секреты на изображении: OCR/автоматической очистки изображения нет. Распознаваемые токены, `vless://` и некоторые персональные URL отклоняются; это не универсальный DLP-фильтр.

Операторам приходит карточка с номером, категорией, вопросом и описанием/скриншотом. Кнопки: взять, запросить сведения, решено, закрыть. Для индивидуального ответа оператор использует **Reply на карточку/сообщение этого бота**; текст/скриншот передаётся пользователю новым сообщением от бота, без forwarding и имени/аккаунта оператора. Запрос дополнительных сведений кнопкой отправляет безопасный стандартный список; произвольный запрос — обычный Reply.

Одновременно проверяются ID закрытой группы, Telegram user ID из allowlist и записанная связь отправленного сообщения с конкретным обращением. ID из callback сам по себе недостаточен. Анонимные/пересланные/чужие сообщения и ответы из других чатов отвергаются. Взятую заявку может изменять только назначенный оператор; передачи другому оператору в v1 нет. Пользовательские действия всегда фильтруются по владельцу обращения.

## Надёжность

История и очередь уведомлений записываются одной транзакцией. Источники Telegram chat/message или callback ID уникальны. Повторы не создают новую заявку/ответ/очередь. На пользователя допускается одно открытое обращение; одинаковое дополнение подавляется в течение минуты. Ограничение — 10 попыток содержательных сообщений/действий в минуту и не чаще одного нового обращения в минуту. База знаний и навигация не расходуют лимит обращений.

Очередь сохраняет попытки, срок следующей отправки, lease, безопасный код ошибки и подтверждённый Telegram message ID. После сбоя незавершённая доставка возвращается по истечении lease. Порядок сообщений в пределах обращения и адресата сохраняется. Сетевые ошибки и 429 повторяются с задержкой; 403 и некорректный запрос переводятся в `blocked` для ручной проверки. Обращение при этом не теряется. Сообщение пользователю говорит «поставлено в очередь», а не утверждает, что оператор уже прочитал его.

Входящий polling использует `Dispatcher.feed_update` напрямую: ошибка сохранения не подавляется внутренним обработчиком long-polling. Позиция обновлений хранится в базе и подтверждается Telegram только после завершения обработки. Разрыв между транзакцией обращения и сохранением позиции безопасен благодаря уникальности источника. Бот не удаляет webhook и не сбрасывает pending updates. Файловый lock запрещает второй процесс с той же базой. Сбой worker останавливает приложение, чтобы systemd мог перезапустить именно новый бот.

Telegram не даёт idempotency key для `sendMessage`/медиа. При неоднозначном сетевом тайм-ауте после фактической отправки повтор уведомления возможен. **Exactly-once доставка не обещается**; уникальность самого обращения/ответа сохраняется. Блокированные доставки видны в health и журнале. Повтор разрешается вручную после устранения причины, без создания нового события.

## Read-only диагностика

`support_bot/diagnostics.py` определяет интерфейс `AccountReader`: подтверждённая привязка Telegram ID → существующий account reference → подписка и разрешённые этому аккаунту узлы. Ответы проверяются на соответствие владельцу. Истёкшая дата не показывается активной подпиской. Данные серверов старше 5 минут/с неверным временем — «Нет данных», а не «Работает».

**Рабочий адаптер не подключён.** По умолчанию подписка и Monitor показывают «Нет данных». Тестовые адаптеры существуют только в тестах, конфигурация не включает демонстрационные подписки. `SubscriptionService.snapshot` и `NodeHealthMonitor` не переиспользуются вслепую: некоторые существующие сервисы могут обновлять статус/данные. Для подключения позже нужен отдельно согласованный источник с минимальным SELECT-доступом/аутентифицированный read-only экспорт, проверкой канонической привязки и свежести измерений. Ни SSH, ни секреты Monitor новому боту не выдавать.

## Что создать владельцу в Telegram

1. Открыть официальный [@BotFather](https://t.me/BotFather), выполнить `/newbot`, название **KudaVPN Support**. Для первого закрытого теста выбрать отдельный свободный username, например с `Support_Test_Bot` (наличие имени не проверялось). Не использовать токены основного, TEST-бота или Monitor.
2. Сохранить новый токен локально. **Не присылать его в чат, issue, PR или скриншоте.** Домен, Mini App, OAuth, платежи и Stars этому приложению не нужны.
3. Создать новую **закрытую группу операторов** без публичного username. Добавить только доверенных операторов и нового бота. Не использовать публичное сообщество KudaVPN и не добавлять посторонних ботов для получения ID.
4. Оставить Group Privacy включённым. Для ответов на сообщения бота его отключать не требуется. Боту достаточно права отправлять текст/фото/документы; администраторские права, управление участниками и доступ к другим чатам не нужны.
5. Каждый тестовый пользователь должен нажать Start в новом боте. Операторы отвечают от своего пользователя, а не анонимно от имени группы.
6. Нужны: username нового бота, отрицательный ID закрытой группы и положительные Telegram user ID разрешённых операторов. Эти ID можно передать отдельно; телефон/пароль/коды входа не нужны. Если ID неизвестны, при следующем согласованном этапе получить их локально из `getUpdates` нового бота после тестового сообщения. Не запускать параллельный polling и не публиковать сырой JSON с персональными данными.

Безопасный локальный ввод после создания бота (выполняет владелец):

```sh
cd /Users/gr/Documents/KudaVPN-social-links
/Users/gr/Documents/KudaVPN-preview/.preview-venv/bin/python -m support_bot.setup_config
```

Токен вводится скрыто. Файл создаётся только вне Git, по умолчанию `/Users/gr/Documents/KudaVPN-private/support/support.env`, 0600, каталог 0700. Существующий файл не перезаписывается, значений в выводе нет. Скрипт **не запускает бота и не обращается в сеть**. После сохранения достаточно сообщить «Конфигурация сохранена»; содержимое не присылать.

## Будущее тестовое развёртывание — только после отдельного разрешения

Шаблоны: `deploy/support-bot/.env.example` и `kudavpn-support.service`. Не выполнять `docker compose up`, проектные миграции, общий deploy или перезапуски существующих юнитов.

1. После разрешения проверить свободные ресурсы и отсутствие конфликтов. Создать отдельного системного пользователя `kudavpn_support`, новый release в `/opt/kudavpn-support/app`, отдельное venv на существующих зависимостях. Не использовать текущий runtime TEST-бота.
2. До изменений сохранить копии только создаваемой/обновляемой конфигурации Support, списка файлов и параметров запуска. На последующих обновлениях сделать согласованный SQLite backup через SQLite backup API; простой `cp` живого файла без WAL недостаточен. Копии содержат переписку и `file_id`: права 0600 и шифрование обязательны, не Git.
3. Установить environment в `/etc/kudavpn-support/support.env` с правами 0600. Создать отдельный state-каталог 0700, доступный только новому пользователю. Токен не передавать в аргументах команд, shell history или stdout.
4. Только от нового пользователя применить миграцию к **новой** базе:

```sh
/opt/kudavpn-support/venv/bin/python -m support_bot.migrate --database /var/lib/kudavpn-support/support.sqlite3
```

5. Установить отдельный шаблон unit и запускать только `kudavpn-support.service`. Не менять общие порты/безопасность/существующие units. Если для изоляции не хватает ресурсов/прав — остановиться. Автозапуск включать только в рамках согласованного развёртывания.
6. Проверить новый `getMe`, закрытость группы, все категории, первое обращение с изображением, статус, ответ оператора, чужой ID, повтор, рестарт **только нового Support**, сохранение очереди и emoji. Сначала без реальных пользователей/чувствительных материалов.
7. Журнал не должен содержать текста обращений, `file_id`, токенов и аккаунтов операторов. Проверить локальную health-команду и доставку в группу. Существующий Monitor сейчас **не изменяется**; интеграцию его проверки согласовать позже.

```sh
/opt/kudavpn-support/venv/bin/python -m support_bot.health --database /var/lib/kudavpn-support/support.sqlite3
```

Код 0: свежий heartbeat, нет blocked и долго ожидающих доставок; код 1: нужна проверка. Вывод содержит только счётчики/время. `--retry-blocked <delivery-id>` повторяет только выбранную заблокированную доставку после ручной проверки; не менять её адресата/содержание.

8. Откат: остановить/отключить **только новый Support unit**, вернуть его прежний release/config. Базу с новой историей не перезаписывать старой копией. Перед будущими несовместимыми миграциями согласовать отдельный план; v001 создаёт только новый schema. Не удалять накопленные обращения и очередь.

## Ограничения до запуска

- Нет реальной проверки Telegram: новый бот, группа и токен ещё не созданы/не предоставлены этой задаче. Android/iPhone/Desktop проверены только на уровне Bot API-моделей и тестовых обновлений; нужна живая приёмка.
- Нет подключения к рабочим подпискам и Monitor. Нет проверки фактического VPN-соединения устройства.
- SQLite: один экземпляр процесса на локальном диске; не shared NFS и не горизонтальный кластер. Медиа хранится ссылками Telegram данного бота. Ротация/замена бота требует отдельного плана.
- В v1 нет перевода обращения другому оператору, альбомов, видео/голоса, полнотекстового поиска, экспорта всей истории, веб-панели или автоматического удаления данных. Альбом обрабатывается отдельными сообщениями с общим ограничением частоты.
- Срок хранения, доступ операторов, текст уведомления об обработке персональных данных и регламент ответа должен утвердить владелец перед публичным запуском. Чувствительные скриншоты нужно редактировать вручную.
- Уведомления о проблемах доставки: безопасные журналы и локальный health; сам существующий Monitor не перенастраивался. Если Telegram недоступен, Telegram-уведомление об этой недоступности гарантировать нельзя.

## Официальные источники

- [Bot API: custom emoji в inline-кнопках](https://core.telegram.org/bots/api#inlinekeyboardbutton): нужен поддерживаемый механизм/право нового бота; существование публичного emoji ID само по себе не гарантирует право его использования. В документации указаны Premium владельца или дополнительные usernames Fragment. Ничего покупать в рамках задачи не требуется.
- [Privacy Mode и BotFather](https://core.telegram.org/bots/features#privacy-mode): ответы на сообщения бота доступны при включённой приватности; `file_id` привязан к боту.
- [Bot API: getUpdates](https://core.telegram.org/bots/api#getupdates) — подтверждение обновлений через offset.
- [aiogram: long polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html) — один polling-процесс на токен; здесь используется отдельный цикл с явным подтверждением после записи.
