# Изолированное HTTPS-развёртывание checkout PR №27

Владелец разрешил 25 октября 2026 отдельный HTTPS-стенд на существующем JustHost, только тестовый магазин 1503208. Никаких реальных списаний, изменений production, VPN-конфигураций, DigitalOcean или платных ресурсов.

## Состав

- Отдельная служба `kudavpn-test-checkout.service`, HTTPS TCP/18543, существующий доверенный сертификат. Нужен явный `CHECKOUT_BIND_HOST=0.0.0.0`; по умолчанию остаётся loopback. Тестовый feed18443 и Xray443/8443/9443/10443 не перезапускаются.
- Отдельный непривилегированный пользователь без shell; systemd LoadCredential передаёт только тестовый shop/secret и сертификат. Токена Telegram в checkout нет. Собственный каталог состояния0700, SQLite0600; env600. Боевой ключ, другой магазин/БД, удалённая БД и существующие VPN-порты запрещены конфигурацией.
- Обновляется только test bot: цены199/499/1790, сохранение исторических заказов, удаление внешнего checkout из Telegram. Основной бот не изменяется. Покупка на независимом сайте не предлагается как обход Stars.
- Публичного webhook нет. `/ready` проверяет тестовую БД, фоновый опрос независимо подтверждает pending-платежи через API. СБП/рекурренты не включены; карта/ЮMoney — на странице test shop.

## Подготовка и откат

`deploy/test-checkout/deploy.sh <полный_commit> <sha256_архива>` предназначен только для проверенного исходного test bot PR26. Перед switch сохраняет test unit/drop-ins/env, pg_dump с проверкой каталога pg_restore, PID/listeners и SHA256 VPN-конфигураций. Миграции не выполняются. Проверяет синтаксис rollback/unit и наличие rollback-артефактов; ждёт readiness до40сек после каждого запуска.

При ошибке после switch автоматически отключается только новый checkout и возвращается совместимая предыдущая версия test bot. Совместимый rollback сохраняет понимание новых версий цен и запрет внешней покупки внутри Telegram. БД назад не копируется, оплаченные события не теряются. Дамп предназначен для ручного аварийного восстановления после отдельного решения; настоящая реставрация БД на работающую базу не выполняется. Readiness и protected listeners/config digests проверяются после switch. Нельзя менять старый release или общие SSH/firewall/VPN-настройки.

TLS credentials перечитываются при перезапуске checkout. Для ограниченного стенда сертификат заранее проверен; существующие renewal hooks не изменяются. Перед длительной эксплуатацией нужен контроль продления сертификата и согласованный reload нового сервиса. Это не production deployment.

## Проверка без списания

Публично проверяются доверенный TLS, `/ready`, static, plans19900/49900/179000,401 без личной сессии,404 webhook и отсутствие демо-роутов. Приватно — доступ владельца, существующий feed/страница и один узел10443 без вывода токена/UUID. Важно: публичная страница без owner-invite намеренно не открывает личные заказы.

Моки/изолированные БД уже проверяют три срока, продление/UUID, дубли, отмену, возвраты, ошибки API, сбой агента, перезапуск и восстановление. Нельзя утверждать, что новый HTTP end-to-end платёж ЮKassa пройден, пока владелец не завершит тестовую оплату на странице провайдера. Нельзя для этого использовать реальные карты/деньги или изменять чужие/production-подписки.

Личный вход выдаётся только вне Telegram через приватный файл на Mac/операторскую команду; одноразовая ссылка живёт10мин, браузерная сессия1час. Ссылка не попадает в Git, отчёт, журналы или сообщения бота. После ручной sandbox-оплаты сверить provider.test=true, сумму/order/user, единственное событие payment, фактический срок, прежний UUID/личную ссылку и уведомление. Повторная проверка не должна менять срок. Сохранить обезличенный результат в handoff.
