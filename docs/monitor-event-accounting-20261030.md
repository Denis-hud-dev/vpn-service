# Monitor: подсчёт событий и выведенный контроллер

Подготовлено 30.10.2026, PR #29. **На серверы не применено.** Согласование требуется до изменения Monitor. Серверные службы, экспорты метрик, токены, рабочие данные и резервирование в этой задаче не менялись; тестовых сообщений в Telegram не отправляли.

## Происхождение кода

В PR #29 до этой задачи Monitor отсутствовал. Существующие `monitor/__init__.py`, `common.py`, `collector.py`, `worker.py` и `tests/test_monitor.py` перенесены из ветки PR #28 `codex/infrastructure-monitor-20261026`, затем изменены только проверки/представление ошибок и retirement. Развёрнутый runtime — release `74f9a3f`; новая реализация не создавалась заново. Старый первоначальный установщик не переносился: повторная установка могла бы нарушить действующее состояние уведомлений. Изменения не импортируются ботом, сайтом или backup jobs.

## Подтверждённая причина

Предыдущая диагностика: окно отчёта 30.10 00:00:40–04:00:40 UTC. Шесть неудачных polling-запросов: пять `TelegramServerError` между 01:19:28 и 01:19:35 UTC и один `TelegramNetworkError` в 01:20:18 UTC. Это две категории, не 18 отдельных неисправностей. Для каждого запроса middleware пишет типизированную WARNING, затем aiogram — обезличенные ERROR и WARNING с текстом `Dependency warning/error; inspect timing and service readiness`.

Старая регулярка считала ERROR в уровне, error в его тексте и error в следующем WARNING: три совпадения на событие. HTTP-ошибка Telegram и её оболочка не являются разными отказами. Причина сетевого исключения из обезличенного журнала недоказуема. Время последнего зарегистрированного отказа не доказывает момент восстановления polling.

## Новый подсчёт

`monitor/events.py` — чистый локальный parser, без побочных действий:

- Docker logs запрашиваются с RFC3339 timestamps за фиксированные последние 14400 секунд. Уровень записи отделяется от её текста. Слово error само по себе не является событием.
- Типизированный `bot.observability: polling_failure kind=...` означает один неуспешный запрос. Только точная следующая ERROR-оболочка `aiogram.dispatcher` в пределах секунды объединяется с ним. Непривязанная обезличенная ERROR делает число неопределённым, чтобы не завысить/занизить его предположительной корреляцией.
- Многострочный traceback принадлежит одной записи. Независимые одинаковые ошибки не склеиваются по сходству текста. В структурированном JSON повторные фрагменты объединяются по явному `event_id`; конфликтующие данные идентификатора означают неопределённость. Для journald используются JSON-записи и уникальный `__CURSOR`, а не строки MESSAGE.
- Категории: Telegram API, сеть, приложение, без классификации. Неизвестный тип не объявляется ошибкой приложения без доказательств.
- Неизвестный формат, обрезанное окно (более 5000 Docker-строк / 1 MiB; journald более 2000 записей / 1 MiB), отсутствие timestamps или ошибка чтения дают **«Количество не определено»**. Частично распознанное последнее событие помечается именно как последнее распознанное.
- Из collector передаются только проверяемые числа, категории и время. Тексты сообщений, traceback, event IDs, URL, ключи и пользовательские данные не экспортируются. Snapshot validation проверяет границы окна, сумму и типы счётчиков.

Шесть наблюдавшихся событий воспроизведены обезличенной fixture с исходными временами: старая регулярка 18, новый результат **6 = 5 API + 1 сеть**, последний сбой 30.10 01:20:18 UTC. Живые журналы повторно не выгружались. Это offline regression, не новая диагностика production.

## Статусы и аварии

🟢 Работает; 🟡 Предупреждение; 🔴 Ошибка; ⚪ Выведен из эксплуатации. Отсутствующие проверки отдельно показываются как 🟡 Нет данных.

История ошибок за четыре часа — предупреждение, а не утверждение о текущей аварии. Реальные текущие отказы readiness/API/PostgreSQL/контейнеров/TCP остаются красными и участвуют в существующем механизме двух последовательных измерений, подавления повторов и уведомления о восстановлении. Нулевая история ошибок сама по себе не доказывает, что VPN работает с телефона. Полные отчёты каждые четыре часа и owner-only доставка сохранены.

## Контроллер и Xray 9443 — разные компоненты

Ранее проверено: `kudavpn-pilot-control.service` завершился 19.10 после RuntimeMaxSec=1d, disabled, Restart=no, MainPID=0; обратных активных зависимостей/потребителей не найдено. Актуальная система выдаёт узел 10443. Контроллер не запускается и не удаляется.

Collector подтвердит retirement только при inactive/failed, disabled, Restart=no, MainPID=0, пустых RequiredBy/WantedBy/BoundBy/ConsistsOf/TriggeredBy и отсутствии включённого узла/доступа 9443 в read-only запросе существующей канонической БД. Недоступные доказательства дают «Нет данных»; неожиданно запущенный/включённый/вновь используемый контроллер — красную ошибку. Никаких изменений БД этим запросом нет.

Только этот конкретный component ID может получить retired, critical=false. Старое состояние инцидента очищается без ложного сообщения «восстановлено». **`kudavpn-pilot-node.service` (Xray 9443) и TCP/9443 остаются самостоятельными критическими проверками**, как и 443/8443/10443. Старый контроллер не является stats API 19086 или действующим агентом 19445.

## Применение только после отдельного подтверждения

Постоянные процессы worker требуют перезапуска **только `kudavpn-monitor.service` на JustHost (primary) и DigitalOcean (watchdog)**. Оба должны понимать новый формат до публикации новых метрик. Коллекторы — oneshot `kudavpn-monitor-collect.service`, запускаемые существующим `kudavpn-monitor-collect.timer`; таймер и его расписание менять не нужно.

План для следующего согласованного этапа:

1. Проверить действующие Monitor unit paths и занятость collection job. Сохранить предыдущий release, unit definitions/права и согласованный snapshot Monitor SQLite (online backup API); не трогать отдельную систему резервирования. Токены/приватная конфигурация остаются на VPS с прежними ограниченными правами.
2. Подготовить новый versioned release без запуска. Сохранить действующий путь collector на старый код и старые export.json на время обновления workers. Нельзя менять общий release symlink так, чтобы timer начал писать новый формат раньше совместимых workers.
3. Последовательно обновить оба worker unit ExecStart и перезапустить именно их, сохранив state/offset/receipts/full_slot и startup grace. Новый worker принимает старый формат (устаревшее число маркеров не выдаётся за реальное число событий). Не запускать второй primary/getUpdates.
4. После проверки обоих workers переключить только collector на новый release; запустить его oneshot на обоих VPS. Проверить свежие schema-valid exports, retired guards, отдельные активные проверки 9443 и следующий штатный отчёт. Не создавать искусственную аварию и не отправлять лишние тестовые сообщения.
5. При ошибке — сначала вернуть прежние collector paths и обновить exports старым форматом, затем вернуть worker paths и перезапустить только Monitor. Рабочие сервисы и их данные не восстанавливать поверх текущих.

До подтверждения владельца эти действия **не выполняются**. Сетевые порты, PostgreSQL, VPN, боты, Monitor на серверах, backup timers и платежи в этой сессии не изменены. Локальные тесты подтверждают готовность кандидата; результат фактического обновления и Telegram-отчёт нужно проверить после согласованного применения.
