# Самостоятельный тестовый checkout KudaVPN Premium

Ветка `codex/standalone-test-checkout-20261025`, [Draft PR №27](https://github.com/Denis-hud-dev/vpn-service/pull/27) поверх №26. Текущие коммит и CI — в [Checks PR №27](https://github.com/Denis-hud-dev/vpn-service/pull/27/checks). Предыдущий код `9dbd008` прошёл CI до обновления цен. Это новый изолированный веб-путь, использующий существующие PaymentCheckoutService, PaymentNotificationProcessor, SubscriptionService, HappService и уведомления. Production-адаптер, реальные платежи и публичные продажи не включены.

## Граница Telegram / самостоятельного сайта

По [официальной документации Telegram](https://core.telegram.org/bots/payments-stars) цифровые услуги внутри ботов/Mini Apps оплачиваются Stars. Наличие своего сайта не отменяет требования для покупок внутри Telegram. Поэтому новая ветка убирает внешний checkout из обработчиков бота, включая owner-only callback: старый paytest:* лишь объясняет ограничение; не создаёт заказ и не выдаёт внешнюю платёжную ссылку. Тестовые тарифы 199 / 499 / 1790 ₽ остаются информацией. Stars-покупка в этой ветке не реализована: стоимость в XTR требует отдельного решения.

ЮKassa-checkout — самостоятельный сайт для независимого открытия в обычном браузере. В боте нет ссылки на его покупку и нет инструкции обходить Stars через внешний браузер. Это не Mini App и не редирект из Telegram для оплаты. Ссылка возвращения после покупки ведёт в кабинет тестового бота для управления уже приобретённым доступом. Перед публичным продвижением окончательно проверить конкретный пользовательский путь на соответствие [условиям Telegram](https://telegram.org/tos/bot-developers#6-2-digital-goods-and-services).

## Реализованный сценарий

1. Для ограниченного теста доверенный локальный оператор выпускает владельцу одноразовый вход вне Telegram. Он привязан к заранее настроенному Telegram ID, действует 10 минут, обменивается на часовую браузерную сессию. В приватной SQLite хранятся только хеши случайных credentials. Это тестовый доступ, а не публичная регистрация покупателей.
2. На сайте выбран тариф; цена всегда берётся с сервера: 19900 / 49900 / 179000 копеек. Клиент не передаёт сумму или ID покупателя. POST требует Origin и CSRF; заказ сериализуется существующим checkout и привязывается к своему User.
3. Тестовый HTTP-клиент создаёт платёж в уже согласованном магазине 1503208 с order UUID, metadata.order_id и Idempotence-Key. Повтор нажатия/тайм-аут возвращает прежний pending-заказ в его окне. Страница показывает выбранный тариф и цену. Данные карты вводятся только на готовой странице ЮKassa.
4. Браузерный redirect не подтверждает оплату. Существующий обработчик независимо получает данные API своего магазина, сверяет test=true, ID, metadata, сумму, валюту, paid/succeeded. Используется опрос; добавлены ограниченные задержки с jitter после ошибок. Webhook остаётся только подсказкой для того же GET, без доверия телу уведомления.
5. Существующая транзакция создаёт/продлевает единственную подписку и пишет единственное событие применения. Не меняет действующий UUID или ключ личной HTTPS-подписки. Нужен актуальный доступ/здоровье узла: при ожидании настройки сайт отдельно показывает «доступ готовится», а не выдуманную готовую ссылку. Бот продолжает доставлять важное подтверждение через существующий PremiumNoticeService.
6. Сайт показывает ожидание, успех, отмену, истечение окна, временную ошибку или возврат; после успеха предлагает существующую персональную страницу подключения Happ. Повторная проверка не прибавляет срок ещё раз.

Окно оформления pending-заказа — 30 минут. По истечении UI скрывает оплату старого заказа. Это не фиктивная отмена у провайдера: если платёж всё же подтверждён позднее, он применяется один раз, а не теряется. Для новой попытки нужен явный новый выбор тарифа. Возврат в кабинет сам по себе ничего не списывает.

## Версии цен и восстановление

Утверждённый новый каталог: `pilot_month_199`, `pilot_quarter_499`, `pilot_year_1790`. Старые `month`/`quarter`/`year` и их 299/799/2490 ₽ сохранены только для истории и законно завершившихся старых заказов. Создание новых заказов принимает только новый каталог; DB, provider payload, сайт и test Premium UI получают одинаковую цену. Обычный production-каталог не изменён. Для истории показываются сохранённые сумма и версия тарифа.

Проверено восстановление после пересоздания engine, session ledger, обработчика, poller и HTTP-приложения: прежний pending-заказ и ключ идемпотентности сохраняются, пропущенное подтверждение подхватывается из API ровно один раз. Это тест перезапуска компонентов на дисковой SQLite; аварийное завершение ОС отдельно не моделировалось. При outage агента подтверждённый платёж остаётся оплаченным, выдача помечается ожидающей; новый worker повторяет сохранённый intent и восстанавливает тот же UUID, без нового платежа/продления. Сам локальный визуальный эмулятор намеренно имеет временную БД: после остановки запускается чистая демонстрация, не база пользователей.

## Возвраты

Новая обработка refund.succeeded сначала получает сам возврат и родительский платёж через API согласованного test shop. Refund object не содержит test-флаг платежа, поэтому режим подтверждается независимым GET родителя. Новых возвратов через POST в этой ветке не создаётся.

Полный возврат последней покупки идемпотентно отмечает Payment.refunded и возвращает срок до этой покупки; предыдущий оплаченный период сохраняется. При единственной покупке доступ становится expired и подлежит существующему отзыву. UUID/личная ссылка не ротируются. Возврат более ранней покупки с последующими изменениями или частичный возврат пишется в закрытый журнал review и **не изменяет срок автоматически**. Сайт честно сообщает ручную проверку. Это намеренный предел безопасной автоматизации; политика частичных возвратов владельцем ещё не утверждена.

Журнал review хранится рядом с приватными browser-сессиями. Для нескольких процессов и публичной эксплуатации его необходимо перенести в транзакционную операционную БД и обеспечить мониторинг; этот пилот — один процесс и один владелец. Фоновый опрос платежей не заменяет самостоятельную сверку возвратов: без зарегистрированного webhook нужен отдельный операционный опрос известных возвратов, пока он не реализован. Историю и банковскую выписку не подменяем демонстрационными событиями.

## НПД

Подтверждённый профиль продавца и порядок чеков навсегда зафиксированы в [SELLER_PROFILE.md](SELLER_PROFILE.md): самозанятый, НПД, НДС не применяется, магазин на самозанятого. Тест не формирует реальный чек и не отправляет доход в «Мой налог». Чек НПД, его передача покупателю и корректировка после возврата — отдельные операции, пока ручные/требующие официальной интеграции. Поля receipt/vat_code/tax_system_code от кассового сценария ИП/ООО не добавлялись.

## Защита

- Каждый заказ читается по связке User и авторизованной сессии; чужой или несуществующий — одинаковый 404. Контрольный владелец задаётся оператором, не параметрами браузера.
- Одноразовый вход приходит во fragment, не в HTTP URL; JS сразу убирает его из адресной строки. Credential/CSRF/ссылки не пишутся в localStorage, access log, аналитику или Git. Выданный вход нельзя пересылать.
- HttpOnly/Secure/SameSite=Lax cookie; без Secure — исключительно локальная имитация на 127.0.0.1. Проверяются Origin и CSRF для изменений, есть ограничение частоты запросов. TLS обязателен для настоящего test shop; сертификаты не генерируются и настройки серверов не меняются этой веткой.
- CSP без сторонних скриптов/шрифтов/аналитики, no-store, no-referrer, frame-ancestors none. QR/подписка не попадают в платёжный payload. Поля карты отсутствуют.
- Любые реальные ключи/другой магазин отклоняются конфигурационной границей entrypoint: только test-owner-only, БД kudavpn_telegram_pilot, shopId 1503208. Test client проверяет test=true в ответах. Полноценного production-режима здесь нет.
- Подтверждённая оплата и фактическая готовность узла различаются. Двойная выдача защищена существующей транзакцией; абсолютная exactly-once доставка Telegram-уведомления при сбое после sendMessage не гарантируется.

## Запуск локальной имитации

Из корня репозитория, с dev-зависимостями:

```sh
python -m scripts.preview_test_checkout --port 18105
```

Открыть `http://127.0.0.1:18105/__demo__/login`. Локальная временная БД, фиктивный покупатель и эмулятор провайдера не связаны с настоящими секретами и узлами. После выбора тарифа кнопка ведёт в явно подписанную **имитацию**, где можно эмулировать успех/отмену без ввода карты. Реальный UUID в этой демонстрации не создаётся. Такой URL не является публичным стендом и недоступен с телефона без отдельной настройки; проброс порта не выполнялся.

## Подготовленный, но не развёрнутый entrypoint

`python -m bot.subscription_api.checkout_main`: отдельный loopback TLS-сервис, по умолчанию 18543. Нужны приватные DATABASE_URL, CHECKOUT_PUBLIC_ORIGIN, CHECKOUT_SESSION_FILE, CHECKOUT_TLS_CERT/KEY, существующие PILOT_YOOKASSA_TEST_SHOP_ID_FILE/SECRET_FILE, PILOT_TRIAL_OWNER_ID, SUBSCRIPTION_PUBLIC_URL/HAPP_LINK_SECRET и KUDAVPN_CHECKOUT_MODE=test-owner-only. Значения не переносить в Git или чат. CHECKOUT_SESSION_FILE должен быть постоянным защищённым файлом вне read-only release, с доступом только службе/оператору. Нельзя использовать production-БД.

Операторская команда выпуска входа — `python -m scripts.issue_checkout_invite --session-file <private-path> --owner-id <test-owner> --origin <approved-https-origin> --output <new-private-file>`. Секрет попадает только в новый файл 0600, не stdout/аргументы. Реальный вход владельцу в этой сессии не выпускался.

До запуска на JustHost отдельно согласовать HTTPS-адрес/порт без использования работающих VPN listeners и способ доступа из обычного браузера. Существующий 18443 не подходит для входящих уведомлений ЮKassa (нужны 443/8443), однако опрос работает и без webhook. Не менять ради этого действующий reverse proxy/firewall/VPN автоматически. Ни серверные службы, ни тестовая БД, ни бот на сервере этой веткой не обновлялись; текущий deployed бот остаётся кодом PR №26. Guard удаления внешней оплаты из бота подготовлен здесь и требует согласованного тестового развёртывания перед новым пользовательским потоком.

Перед развёртыванием: закрытая копия test unit/env/app/БД/session ledger, проверка восстановления, один тестовый owner, выключенные реальные продажи; rollout отдельного сервиса и только необходимых test-bot файлов, readiness и сверка подписок; откат только приложений/config, без отката живых платежей/БД поверх новых записей. Новых оплачиваемых ресурсов не требуется.

## Осталось до реальной продажи

Публичная аутентификация покупателей (например, актуальный Telegram OIDC с проверкой issuer/audience/nonce/PKCE; сейчас только операторский owner-invite), поддержка/условия/согласия, процесс чеков НПД и доставки, политика частичных/ранних возвратов, мониторинг оплаченных, но не применённых событий и очереди review, отдельный проверенный production-адаптер/настройки магазина и официальное подключение СБП. СБП в тестовом магазине недоступна; не показываем её рабочей. После отдельного разрешения — новая ограниченная реальная проверка, а не переключение test-only клиента боевым ключом.

## Проверки и продолжение

Новые HTTP/session/refund/integration проверки: **21 passed**. Включены три цены, повтор создания/уведомления, CSRF/Origin, чужой заказ, истечение сессии/заказа, поздняя подтверждённая оплата, несовпадение суммы, отмена, outage/backoff, полный/частичный/ранний возврат. Отдельный тест использует настоящий существующий Happ issuer и NodeReconciler с имитированным узлом: после двух покупок сохраняются UUID и HTTPS-ссылка, срок растёт один раз на каждую; после полного возврата доступ отзывается существующим механизмом. Ни реальный сервер, ни деньги не затронуты.

В браузере пройден локальный путь выбора 199 ₽ → явно подписанный эмулятор провайдера → успех и кнопка подключения; после уточнения цен дополнительно 499 ₽ → успех с датой окончания из БД и 1790 ₽ → отмена. При первой проверке устаревшая демонстрационная сессия дала безопасный отказ CSRF; после нового локального входа путь работает, защиту не отключали. Эмулятор использует same-origin fetch для подтверждения, чтобы сочетаться с no-referrer и строгой Origin-проверкой. На ширинах **390 и 375 px** scrollWidth равен ширине окна, горизонтальной прокрутки нет; desktop-предпросмотр 1280 px проверен. Физические Android/iOS и платёжный сайт ЮKassa этим не проверены.

Снимки: [desktop](screenshots/checkout-desktop.jpg), [mobile success](screenshots/checkout-mobile-success.jpg). Полный локальный набор: **246 passed, 9 skipped**. Последняя профильная проверка 21 checkout-сценария после проверки восстановления HTTP-приложения прошла. Пропуски не считать успешными; CI дополнительно использует одноразовую PostgreSQL.

Для тестирования реальной страницы ЮKassa на Android/iOS нужен отдельно разрешённый HTTPS-стенд и действие владельца; локальная имитация и responsive viewport не доказывают физический платёж/импорт на устройстве. В этой сессии новые тестовые или настоящие платежи у ЮKassa не создавались, реальные ключи не использовались. Первый следующий технический шаг — согласовать изолированный HTTPS test checkout и новый безопасный вход владельца, затем провести только одну тестовую оплату через обычный браузер. Реальные продажи остаются запрещены.
