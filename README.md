# KudaVPN

KudaVPN — коммерческий VPN-сервис с управлением через Telegram на Python 3.12 и aiogram 3. Проект включает PostgreSQL, миграции, слой бизнес-сервисов и интерфейс KudaVPN Premium. Реальные платежи не подключены. В отдельной ветке разрабатываются персональные Happ-подписки и управление Xray. Локальный тест REALITY + Vision теперь передаёт HTTPS; перед развёртыванием нужны проверка реального VPN-узла и сетей пользователей.

Локальная архитектура Xray, настройки доверия, проверки и известные ограничения описаны в [docs/xray-access-automation.md](docs/xray-access-automation.md). Работающий Telegram-бот не использует этот новый агент автоматически.
Текущий подтверждённый статус прямого подключения из России и следующий безопасный тест — в [диагностическом решении](docs/diagnostics/vpn-path-decision-2026-10-14.md). Успешная работа Happ на Android пока не подтверждена.

## Что работает

Главное меню использует inline-кнопки: подключение VPN, личный кабинет, тарифы, трафик, бонусы и поддержка. Тарифы сохранены: **1 месяц — 299 ₽**, **3 месяца — 799 ₽**, **12 месяцев — 2490 ₽**. Выбор тарифа показывает прежнюю заглушку; он не создаёт платёж и не активирует подписку.

При заполненном `DATABASE_URL` первый `/start` создаёт пользователя в PostgreSQL, последующие вызовы обновляют имя и username. Создание атомарное через UPSERT; Telegram ID уникален. `referrer_id` сохраняется при первом обращении и не меняется; саморефералы игнорируются. Это Telegram ID, а не внешний ключ: приглашение может прийти раньше регистрации пригласившего пользователя.

«Личный кабинет» и вложенный раздел «Устройства» читают базу. У нового пользователя нет подписки и устройств. `SubscriptionService` поддерживает `pending`, `active`, `expired`, `blocked`, проверяет даты активации и допустимые переходы, предоставляет массовое завершение просроченных подписок `expire_due()`. Открытие подписки также переводит просроченную `active` в `expired`. Периодический scheduler пока не подключён; VPN-сервис отдельно проверяет срок действия.

При пустом `DATABASE_URL` сохраняется рабочий деморежим первого этапа с данными в памяти. При указанном, но недоступном URL бот не переключается незаметно в деморежим: запуск требует доступной базы и применённых миграций.

## База данных

Все модели имеют UUID, `created_at`, `updated_at`; временные поля PostgreSQL хранят timezone. Связи и ограничения проверяются базой, удаление связанного пользователя или сервера ограничено `RESTRICT`.

| Модель | Основные поля и правила |
| --- | --- |
| User | Уникальный `telegram_id`, профиль, `referrer_id` первого обращения |
| Subscription | Одна текущая подписка на пользователя, tariff ID, status, starts/expires, device_limit |
| Device | Пользователь, подписка, сервер, платформа, статус, публичный ключ, IP; составной FK проверяет владельца подписки |
| VPNServer | Имя, hostname, порт, локация, публичный ключ, подсеть; по умолчанию выключен |
| Payment | Пользователь, необязательная подписка, тариф, сумма целым числом в копейках, RUB, provider ID, idempotency key, статус |

Уникальность `(provider, provider_payment_id)` и `idempotency_key` подготовлена для будущей обработки оплаты. История продлений будет храниться в платежах; отдельная история изменений подписки пока не реализована. Для активного устройства обязательны сервер, публичный ключ и IP; пара сервер/IP уникальна. Приватные WireGuard-ключи и API-ключи в таблицы не записываются. Лимит устройств пока хранится как настройка (по умолчанию 5); выдачи устройств, проверяющей этот лимит, ещё нет.

## Переменные окружения

Настоящий `.env` исключён из Git и Docker build context. Не перезаписывайте существующий `.env`: добавьте новые поля вручную. Если файла ещё нет, создайте копию `.env.example` локально. Приложение читает environment variables и само `.env` не загружает.

- `BOT_TOKEN` — локальный токен BotFather; обязателен для бота, не нужен для миграций.
- `SUPPORT_USERNAME` — необязательный Telegram username поддержки.
- `POSTGRES_DB`, `POSTGRES_USER` — имя базы и пользователь (пример: `kudavpn`).
- `POSTGRES_PASSWORD` — придуманный локальный пароль; Compose требует непустое значение.
- `DATABASE_URL` — для запуска бота и Alembic на хосте, драйвер **postgresql+psycopg**.
- `DATABASE_URL_DOCKER` — отдельный URL с hostname `postgres`; Compose передаёт его контейнерам как `DATABASE_URL`.
- `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_RETURN_URL` — пока оставьте пустыми.

Шаблоны URL (замените значения локально, пароль URL-encode при наличии специальных символов):

```text
DATABASE_URL=postgresql+psycopg://USER:ENCODED_PASSWORD@127.0.0.1:5432/DB
DATABASE_URL_DOCKER=postgresql+psycopg://USER:ENCODED_PASSWORD@postgres:5432/DB
```

В `.env`, который загружается через shell `source`, заключайте значения со специальными символами в одинарные кавычки. Для простоты настройки можно использовать длинный случайный буквенно-цифровой пароль. Не вставляйте реальные секреты в README или команды, сохраняемые в истории терминала.

## Локальный запуск с PostgreSQL

Из корня репозитория, после заполнения локального `.env`:

```sh
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r bot/requirements.txt
set -a
source .env
set +a
```

Если `.venv` уже есть, достаточно активировать её и обновить зависимости. PostgreSQL можно запустить через Docker Compose; для этих команд также заполните `DATABASE_URL_DOCKER`, поскольку Compose проверяет переменные всего файла:

```sh
docker compose up -d postgres
alembic upgrade head
alembic current
python -m bot.main
```

Откройте Telegram и отправьте `/start` — пользователь появится в `users`. Посмотреть количество пользователей без вывода токенов:

```sh
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM users;"'
```

Если Docker отсутствует, используйте уже установленный PostgreSQL и заполните `DATABASE_URL`. Для деморежима оставьте `DATABASE_URL` пустым. Не запускайте два polling-процесса с одним токеном. Остановка локального бота: `Ctrl+C`.

## Полный запуск через Docker Compose

Остановите прежний локальный бот, заполните переменные и выполните:

```sh
docker compose up --build -d
docker compose logs -f bot
```

Порядок запуска: PostgreSQL проходит healthcheck → контейнер `migrate` применяет Alembic → бот стартует только после успешной миграции. База сохраняется в named volume `postgres_data`. Пароль существующей базы не меняется автоматически при изменении `.env`.

```sh
docker compose stop bot
docker compose down
```

`down` без `-v` сохраняет данные. После следующих изменений кода/миграций выполните `docker compose up --build -d`.

Контейнер бота работает непривилегированным пользователем. SIGINT/SIGTERM закрывают polling, Telegram-сессию, storage, health-сервер и SQLAlchemy engine. PostgreSQL публикуется только на `127.0.0.1:5432`. HTTP-порт бота по умолчанию наружу не публикуется.

`/health` на 8080 проверяет живой процесс. `/ready` требует завершённого старта и доступной мигрированной базы, возвращая 503 при сбое базы. Проверка не гарантирует доступность Telegram при последующем сетевом сбое. Для локальной диагностики можно добавить публикацию `127.0.0.1:8080:8080`. При изменении `HEALTH_PORT` также обновите Docker healthcheck.

## YooKassa и WireGuard: подготовленная архитектура

`PaymentRepository.create_pending()` сохраняет платёж с ценой в копейках и ключом идемпотентности; повторный вызов с тем же ключом и параметрами возвращает ту же запись. Telegram-кнопки пока этот метод не вызывают. `PaymentGateway` описывает создание и проверку платежа; `YooKassaGateway` сейчас всегда выдаёт ошибку «не подключена». Реальные ключи не читаются и запросы оплаты не отправляются.

Следующий этап оплаты: HTTP adapter YooKassa/СБП, confirmation URL, проверка статуса у провайдера, безопасный webhook, идемпотентная обработка событий и транзакционная активация/продление подписки. `SubscriptionService.set_status()` предназначен для доверенного backend-кода, он не является подтверждением оплаты и не доступен пользователю Telegram.

`WireGuardGateway` описывает добавление/удаление peer; текущий адаптер выключен. `VPNService` проверяет подписку и наличие включённого сервера, но даже такая запись в базе пока не выдаёт доступ: `provision_device()` всегда отказывает. Далее нужны adapter управления сервером, адресный пул, лимиты устройств, безопасная передача конфигурации, повторные попытки и отзыв peer при блокировке/истечении. Пока переход статуса в базе не отзывает реальный peer — реальных peer на этом этапе нет.

## Проверки

```sh
pip install -r bot/requirements-dev.txt
python -m compileall -q bot migrations tests
python tests/smoke.py
python -m pytest -q
pip check
```

Smoke test проверяет Premium-экраны и callback-кнопки без Telegram API. Тесты навигации проверяют один message ID, ответы на все callback, повторные и параллельные нажатия, stale/inaccessible сообщения, HTML-экранирование, ограничения Bot API, отказ удаления /start, ошибки редактирования, rate limit, сетевой сбой и недоступную базу. Lifecycle-тест запускает структуру приложения с подменённым polling и Telegram API, без второго реального бота. Интеграционный тест на временной SQLite проверяет миграции `upgrade → downgrade → upgrade`, совпадение схемы с моделями, сохранение пользователей/referrer_id, статусы подписки, ограничения FK, устройства, pending payments и отключённые внешние адаптеры. SQLite используется только в тестах; production-конфигурация допускает PostgreSQL.

Проверка PostgreSQL SQL без подключения (при заданном URL):

```sh
alembic upgrade head --sql > /tmp/kudavpn-schema.sql
```

Для интеграционного теста на настоящем PostgreSQL задайте **отдельную пустую тестовую базу** через `TEST_DATABASE_URL=postgresql+psycopg://...` в локальном окружении и выполните `python -m pytest -q`. Тест применяет и откатывает таблицы: не используйте рабочую базу. Без этой переменной PostgreSQL-тест явно пропускается.

Подход к асинхронным сессиям и миграциям основан на [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html) и [Alembic cookbook](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic).


## Интерфейс KudaVPN Premium

`/start` создаёт один фирменный экран, передавая inline-кнопки сразу в `sendMessage.reply_markup`. Отдельного запроса добавления кнопок нет: это исключает приветствие без меню при отказе редактирования. Если в клиенте осталась reply-клавиатура старой версии, её можно свернуть средствами Telegram. Повторный `/start` в том же процессе обновляет известный экран. Команда пользователя удаляется по возможности; отсутствие прав на удаление не считается сбоем.

Все переходы, включая «Назад» и «Главное меню», редактируют существующее сообщение. Callback подтверждается до обращения к базе. Операции одного чата выполняются последовательно: двойные нажатия не создают сообщения, одинаковые экраны не редактируются повторно. Старые кнопки `menu`, `buy`, `device:add`, `instructions` перенаправляют в новый интерфейс; неизвестные кнопки показывают путь в меню.

Кабинет показывает сохранённые статус, тариф, дату окончания в UTC и количество устройств. Деморежим отображает «Не активна» и «Нет данных» для неизвестных полей; в PostgreSQL нулевое количество устройств — реальное значение. Метрики трафика пока отсутствуют и не заменяются выдуманными цифрами. Бонусы пока недоступны, обещаний начислений нет. Поддержка использует существующий `SUPPORT_USERNAME`.

Выбор тарифа показывает его цену, но не вызывает сервис создания оплаты. Подключение через Happ объясняет будущие действия после получения персональной ссылки; ссылки и конфигурации сейчас не выдаются. Общая инструкция соответствует [документации Happ](https://www.happ.su/main/faq/adding-configuration-subscription). При подключении сервера потребуется совместимый с Happ профиль: имеющийся адаптер WireGuard сохраняется, но не преобразуется автоматически в подписку Happ.

Состояние активного экрана хранится в PostgreSQL в отдельной таблице `active_screens`: Telegram user ID, chat ID, message ID и дата обновления. Миграция `0002_active_screens` только добавляет таблицу и не меняет существующие записи. Повторный `/start`, включая вызов после перезапуска процесса, загружает сохранённый ID и обновляет тот же экран. При подтверждённом отказе Telegram редактировать сообщение бот создаёт замену, сохраняет новый ID и пытается удалить только предыдущий зарегистрированный экран навигации. Rate limit/сетевой сбой сохраняют старый экран; нажмите кнопку ещё раз после восстановления. Устаревшие кнопки подтверждаются и игнорируются. Если удалить старый экран нельзя, он остаётся в истории, но его кнопки не управляют активным экраном. Чеки, уведомления и обращения в поддержку не удаляются. В деморежиме без PostgreSQL используется память процесса. У экрана, созданного до этой миграции, ID ещё не сохранён: его можно зарегистрировать первым нажатием узнаваемой Premium-кнопки; неизвестные старые сообщения бот не ищет и не очищает. Если такого нажатия не было, первый `/start` создаёт зарегистрированный экран, а дальнейшие вызовы его переиспользуют. Ограничения соответствуют [Telegram Bot API](https://core.telegram.org/bots/api#editmessagetext).

## Жизненный цикл подписок (локальная разработка)

Миграция `0003_subscription_history` добавляет историю, не меняя существующие
подписки. Перед запуском новой версии требуется `alembic upgrade head`.
`SubscriptionService.apply_confirmed_payment(ConfirmedPayment(...))` — внутренний
контракт доверенного backend: будущий адаптер обязан самостоятельно проверить
успешный статус у провайдера до вызова. DTO не доказывает подлинность webhook.
Telegram не вызывает этот интерфейс; настоящих платежей пока нет.

Сумма и валюта сверяются с локальным платежом и тарифом. Активация и отметка оплаты
сохраняются одной транзакцией. Уникальная ссылка истории на платёж защищает от
повторного применения; блокировка пользователя сериализует покупки PostgreSQL.
Продление начисляет календарные месяцы от будущего окончания активной подписки,
иначе от времени обработки. Последний день месяца ограничивается числом дней
целевого месяца. Заблокированная подписка не активируется платежом; оператор
должен решить блокировку перед повторной обработкой. Платёж при отказе остаётся
pending. `set_status()` больше не позволяет обходить подтверждение оплаты.

Периодическая задача каждые 60 секунд переводит просроченные active в expired.
Она отменяется при завершении приложения; ошибки логируются без данных платежа.
История содержит предыдущие и новые статусы/сроки и связанный платёж. Старые
операции до миграции не восстанавливаются задним числом. Контракт AccessGateway
подготовлен для будущей сверки Xray; сейчас не вызывает сервер и не выдаёт доступ.
Истечение в базе пока не отзывает отдельно созданные Xray-профили.

Проверки: обычный pytest использует временную SQLite. Для настоящей конкуренции
задайте `LIFECYCLE_TEST_DATABASE_URL` только для отдельной тестовой PostgreSQL
(`postgresql+psycopg://...`) и запустите
`python -m pytest tests/test_subscription_lifecycle.py -q`.
Тест создаёт и удаляет только собственную случайную схему. Рабочую базу не задавать.
Следующие задачи: верификация провайдером, обработка возвратов, outbox/reconciliation
для Xray, защита endpoint и эксплуатационный мониторинг фонового исполнителя.

Проверка оплаты теперь обязательна внутри SubscriptionService: внедряемый
PaymentVerifier должен независимо получить успешный платёж у провайдера.
По умолчанию DisabledPaymentVerifier отклоняет любую активацию, даже с правильно
составленным ConfirmedPayment. Ошибка провайдера или несовпадающие данные не меняют
платёж, подписку и историю. Разрешающий адаптер используется только в тестах.
PostgreSQL-тест дополнительно проверяет конкуренцию истечения и продления.
